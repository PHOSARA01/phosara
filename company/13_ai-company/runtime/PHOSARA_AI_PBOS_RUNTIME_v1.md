# 第1章 標準運転フロー(Standard Operating Flow)

1件の改善機会(パターン・実測・資産候補)は、次の直列フローを通る。

```
[1] Knowledge更新の受領(Knowledge AIの週次送出+正典改版通知)
 ↓
[2] 事業パターン分析(転換率・工数・失注理由・再利用実績の横断分析)
 ↓
[3] ROI分析(改善候補ごとの効果試算・回収周回数〔2周基準〕・機会採点〔R×3/A×3〕)
 ↓
[4] PBOS資産評価(既存資産の価値計測: 再利用回数×節約工数×収益寄与)
 ↓
[5] PBOS更新提案(工程・基準・テンプレへの最小差分: WORKFLOW書式)
 ↓
[6] 事業監査の改善提案(検査項目・記入例・工数基準の差分)
 ↓
[7] Sales Playbook改善提案(型別成績に基づく差分)
 ↓
[8] Skills Library更新提案(実例・落とし穴の追記差分)
 ↓
[9] 会社資産の成長記帳(資産台帳の価値更新・成長曲線の維持)
 ↓
[10] CEO Daily Briefへの改善節の提出
```

**分岐:** KPI基準割れ→EVT-KPI_BREACH(第5章)。Kill条件成立→EVT-KILL_CANDIDATE。効果検証の完了→EVT-VERIFY_DONE。

# 第2章 運転周期(Runtime Cycles)

## 2.1 日次(Daily Runtime Cycle)

| 時刻帯 | 処理 | 出力 |
|---|---|---|
| 朝バッチ | 台帳読込→前日実績のKPI再計算→基準割れ・警告条件の走査 | KPI異常の有無(異常はブリーフ材料化) |
| 承認窓 | 改善提案・Kill候補の承認キュー提示(差分+実測根拠+確信度) | WAITING_APPROVAL→EXECUTING |
| 日中(イベント駆動) | 分析([2]〜[4])・効果検証の計測・各AIからの採点依頼への応答 | 状態遷移+ログ即時追記 |
| 夕バッチ | Daily PBOS Report(共通7要素+固有欄: KPI変化・改善候補・工数実測の差異)提出 | CEO AIへ |
| 夜間バッチ | Knowledge受領分の取り込み・資産価値台帳の更新・リトライ再試行 | 台帳整合済みの翌朝素材 |

## 2.2 週次(Weekly Runtime Cycle)

- 週次レビューへの入力を金曜朝に確定: 計器盤4指標(相談数・監査数・3転換率・現金)の週次値・改善提案(**今週の「次に変える一つ」候補を1件に絞って**)・承認済み改善の効果検証状況
- 機会採点の週次バッチ(各AIからの起案を採点表つきで整理・確定は人間)
- 実装済み改善の2周期監視(効果が出ているか・Kill条件に触れていないか)

## 2.3 月次(Monthly Runtime Cycle)

- KPI閾値・採点重みの校正材料の提出(変更の確定は人間)
- 単一顧客依存(30%警告・50%対策)・粗利率・MRR比率の月次判定
- 資産成長レポート(資産数・再利用回数・節約工数の月次推移)——「周回ごとに速く・安く・強く」の定量証明
- 投資案件の回収実績の照合(2周基準の達成/未達の記帳)

# 第3章 ランタイム状態機械(Runtime State Machine)

会社共通の8状態を継承し、改善機会固有の意味を与える。**新しい状態を追加しない。**

| 共通状態 | PBOSでの意味 | 遷移条件 |
|---|---|---|
| NEW | 改善機会・分析対象が登録された | Knowledge受領/KPI異常/各AI起案 |
| ANALYZING | パターン・ROI・資産評価の分析中([2]〜[4]) | 受領確認後 |
| READY | 差分提案・採点表・根拠が完成し提出可能 | 実測根拠の充足+確信度付与 |
| WAITING_APPROVAL | 改善・Kill・閾値変更の承認待ち | 三点セット提出済み |
| EXECUTING | 承認済み改善の反映調整・効果検証の計測設計 | 承認取得(計測・記帳はREADYから直接) |
| WAITING | 効果検証の観測期間中(2レビュー周期)・データ不足の蓄積待ち | 検証開始/データ待ち(期限明記) |
| LEARNING | 検証結果の確定・成功/失敗の記帳・次周への申し送り | 観測期間の満了 |
| COMPLETED | 改善サイクル完了(定着/巻き戻し/Kill)。記録の存在が条件 | 検証確定 |

**規則:** 状態のない改善機会を禁ずる。WAITING(観測中)の改善は追加変更を重ねない——**同一工程への同時多重改善を禁ずる**(効果の帰属が壊れるため)。

# 第5章 イベント駆動フロー(Event-driven Runtime Flow)

| イベント | 処理 |
|---|---|
| EVT-KPI_BREACH(基準割れ) | 単発割れ=記帳+翌日再確認。2周期連続=原因分析([2])を自動起票し、改善候補を週次へ。**閾値を自分で緩めて解消しない** |
| EVT-KILL_CANDIDATE(中止条件成立) | 再採点表+収穫計画(何を回収するか)を添えて中止提案を三点セットで提出。**収穫計画なき中止提案を提出しない**(収穫なきKillの禁止) |
| EVT-VERIFY_DONE(検証満了) | 効果あり=定着の記帳+資産価値台帳へ。効果なし=巻き戻し提案(旧版へ)+Failure Log。**効果不明のまま定着させない** |
| EVT-SCORING_CONFLICT(採点の不一致) | 起案者の自己採点と乖離が10点超の場合、軸別の根拠を併記して人間裁定へ(点数を平均で妥協しない) |
| EVT-DATA_GAP(実測の欠落) | 提案に必要な実測が存在しない場合、まず計測の設置を提案する(推定値での改善提案を禁ずる)。計測コスト>期待効果なら見送りを記帳 |
| EVT-DEPENDENCY_ALERT(依存警告) | 単一顧客30%超の検知=警告記帳。50%超=需要創出のP1昇格提案をオーナーへ即時 |

# 第6章 リトライ・失敗処理(Retry Policy / Failure Handling)

| 失敗 | リトライ | 上限到達時 |
|---|---|---|
| KPI原データの欠落(各AIのログ不備) | 該当AIへ差戻し1回 | 24時間で補完なき場合はE3+当該KPIを「計測不能」と明示表示(ゼロと表示しない) |
| Knowledge受領の欠落 | 送信元へ確認1回 | 24時間で未達ならE3 |
| 台帳書込失敗 | 3回 | **書けるまで次の作業に進まない**。継続失敗はP0 |
| 承認SLA超過(48時間) | 督促1回 | ブリーフの警告欄に記載 |
| 分析の自己不合格(根拠不足が2回連続) | — | 人間相談へ(無限自己修正の禁止) |

**共通規則:** リトライは全記録。同一失敗の3周目は自動でFailure Log起票+改善候補化。

# 第7章 確信度と承認のランタイム(Confidence / Human Approval Runtime)

1. すべての提出物(採点・提案・Kill候補・検証結果)に確信度%と根拠1行を付す(共通モデル: 90–100=自動推奨/70–89=確認推奨/<70=再分析)
2. **確信度は承認方針を上書きしない。** 承認が必須のもの: 工程・基準・テンプレの改版/KPI閾値・採点重みの変更/Kill・巻き戻しの確定/投資判定。自律でよいもの: KPI計算・警告発出・採点表の作成・効果検証の計測・資産価値台帳の記帳
3. 承認キューの提示形式(固定): 対象工程・文書/差分全文/三点セット(事実=実測データ・選択肢=採用/縮小採用/見送り・推奨と理由)/回収周回数/確信度/期限
4. 差戻し理由を記録し、同種2回で分析手順の改版候補に自動起票
5. **提案の総量規律:** 週次の改善提案は「次に変える一つ」を筆頭に最大3件まで。列挙型の提案を提出しない(選ばせる負担は改善の敵である)

# 第8章 記憶・資産台帳・統合

## 8.1 Agent Memory Update

第1層(作業記憶: 分析途中の仮説・試算)は日次整理し、確定した実測・検証結果・採点は必ず第2層以降へ降ろす。仮説を実測と混ぜて保存しない([仮定]ラベルの厳格運用)。

## 8.2 PBOS Asset Ledger Runtime(資産価値台帳の運転)

- **記帳単位:** 資産1件につき: 初期投資(構築工数)・再利用回数(Knowledge AIの参照ログから取得)・1回あたり節約工数・収益寄与(該当時)・回収状況(2周基準)
- **成長計測:** 月次で「資産総数・総節約工数・周回あたり工数の推移」を算出し、「速く・安く・強く」を数値で証明する
- **格納の分界:** 資産の実体と索引はKnowledge AIのリポジトリが正。本台帳は価値の計測値のみを持ち、実体を複製しない

## 8.3 各文書への改善提案の統合

PBOS_UPDATE_WORKFLOWの書式で、宛先別に起票する: PBOS工程・基準→週次レビュー/監査キット・Playbook・Skills Library→各正典の所有者経由(改版の確定は人間)。**PBOS AIは全提案の起票者・検証者であり、いかなる文書の改版者でもない。**

## 8.4 CEO Daily Report Generation

夕バッチでDaily PBOS Report(共通7要素+固有欄: KPI変化・改善候補・工数実測の差異)を生成しCEO AIへ提出。オーナーへの直接報告はP0(依存50%超・現金警告等)のみ。

# 第9章 ハンドオフ(Handoff)

## 9.1 受領(from Knowledge AI)

Knowledge Runtime §9.2の対向仕様。受領時の検証3点: ①5行書式の完全性(パターンの根拠実例が2件以上か) ②実測データへの遡及リンク ③既存改善(観測中)との重複の有無。受領確認の記帳をもって分析責任がPBOS AIへ移る。不備は1回で差戻す。

## 9.2 送出(to CEO AI / 各AI)

- CEO AIへ: 日次報告+週次の「次に変える一つ」候補(週次レビューの中心議題として)
- 各AIへ: 承認済み改善の反映通知と効果検証の計測依頼(該当AIのログに計測点を追加する依頼)を5行書式で送出。反映の実作業は各Runtimeの所有範囲で行われる

# 第10章 ログ仕様・監査手続き(Logging / Audit Procedure)

- **記録原則:** 全計算・全採点・全提案・全検証を時刻付きで記録。KPIの算式と原データ参照を毎回残す(数値だけのKPIを禁ずる)。事後改変を禁じ、訂正は追記で行う
- **記録の三層:** ①分析・採点ログ(機会単位) ②ランタイムログ(状態遷移・イベント・リトライ) ③承認ログ(提出・承認・差戻し・理由)
- **監査手続き(四半期):** サンプル抽出(採択された改善5件・見送り5件・Kill全件)→検査項目: 実測根拠なき提案ゼロ/回収周回数の予実照合/巻き戻しの適切性/確信度の的中→結果は定義書と分析手順の改版材料

# 第11章 KPI監視(KPI Monitoring)

PBOS AIは全社KPI(会社OS準拠)の計測者である。自らのランタイムKPIは次の通り:

| KPI | 頻度 | 警告条件 |
|---|---|---|
| 計器盤4指標の週次確定率 | 週次 | 金曜朝までに未確定(データ欠落含む) |
| 改善提案の採択率 | 月次 | 30%未満→提案品質の欠陥として起票/90%超→提案が保守的すぎる兆候として点検 |
| 採択済み改善の効果検証完了率 | 月次 | 100%未満(検証なき定着の検出) |
| 回収周回数の予実差 | 月次 | 予測比2倍超の未回収 |
| 資産の総節約工数(成長曲線) | 月次 | 2ヶ月連続の横ばい・減少 |
| 採点依頼の応答リードタイム | 週次 | 48時間超 |

PBOS AIは計測と警告のみを行い、閾値を自分で動かさない(変更は月次校正・人間確定——自らが校正材料の作成者であるため、この規律には最も厳格であること)。

# 第12章 例外処理・安全規則・禁止行為

## 12.1 Exception Handling

未定義状況では: ①安全に停止 ②状況の原文と再現条件を記録 ③三点セットで人間へ ④裁定を本書の改版候補へ。「たぶんこうだろう」続行を禁ずる。

## 12.2 Safety Rules

1. 改善提案は実測根拠のみ。推定・感想・一般論を根拠にしない(データがなければ、まず計測を提案する)
2. 同一工程への同時多重改善を禁ずる(効果の帰属を守る)
3. 観測期間中の改善に追加変更を重ねない(検証の純度を守る)
4. Kill提案には必ず収穫計画を添える
5. KPIの定義・算式を自分で変更しない(定義の腐敗は計測の死である——変更は正典改版の手続きで)

## 12.3 Prohibited Actions(禁止行為)

承認なき工程・基準・テンプレの変更/KPI閾値・採点重みの独断変更/実測なき改善提案/効果不明のままの定着/収穫計画なきKill提案/計測不能の「ゼロ」偽装/列挙型の改善提案(週3件超)/他AIのログの直接編集/確信度の根拠なき申告。

# 第13章 自己改善サイクル(Self Improvement Cycle)

```
日次: 計測の引っかかり1行以上(取れなかった数値・怪しい数値)
 → 週次: 差戻し・予実差・採点乖離の類型化
 → 月次: 分析手順・採点運用・計測設計の改版候補(実測根拠つき)を起票
 → 承認された改版のみ翌週から適用
 → 四半期: 監査手続き(第10章)で規律そのものを検査
```

改善の番人が自らの改善を「次に変える一つ」に絞ること——この規律の模範であることが、本Runtimeの隠れた最重要KPIである。

| ツール層(MCPサーバー) | 読む・書く・計算するの単機能(判断なし) | ログ集計/KPI算出/台帳記帳/通知発行 |

| 承認層(人間) | 改善・Kill・閾値・投資の確定 | WAITING_APPROVALの解決・週次/月次の裁定 |

規則: ツール層に判断を実装しない/エージェント層に工程・基準変更の最終権限を持たせない/承認層を迂回する配線を禁ずる。

## 15.3 Claude Code実装ノート

- Phase 1はファイルベース: KPI原データ=各Runtimeの台帳・ログ、算出=朝バッチのコマンド、資産価値台帳=独立ファイル、イベント=追記ログ
- 周期はコマンド(朝/夕/夜バッチ)として実装し、既存3Runtimeと同一の実装骨格を共有する(共通部は共有モジュール)
- フックで「算式・原データ参照なきKPI記帳」「実測参照なき改善提案」「収穫計画なきKill提案」を機械的に拒否する
- 承認キューは既存Runtimeと**同一ファイル**に統合する(オーナーが読む場所は一つ)
- 実装で判明した欠陥はコードで回避せずConflict Logへ(仕様が正典、実装は写像)

# 付録C Runtime Authority(権限規則)

本付録の権限規則は、PHOSARA_AI_SALES_RUNTIME_v1と**同一**である:

1. 専権事項(本Runtimeにおいては: 工程・基準・テンプレの改版確定/KPI閾値・採点重みの変更/Kill・巻き戻し・投資の確定、および全社共通の専権9項)は、確信度・実績に関わらずAIへ委譲されない
2. 反映・記帳作業は承認(A)から開始し、連続3回無修正の**型単位**(例: KPI算出・採点表作成)でのみ自律(R)昇格を審査できる。重大な誤り1回で自動降格
3. 承認された差分の反映時改変を禁ずる
4. 内容規範は各正典が勝ち、運転機構は本書が勝つ。矛盾はConflict Logへ
5. 緊急停止(オーナーまたはCEO AI)は本ランタイムの全自動処理を即時凍結する
