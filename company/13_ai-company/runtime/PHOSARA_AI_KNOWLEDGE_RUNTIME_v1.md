# 第1章 標準運転フロー(Standard Operating Flow)

1件の知識アイテム(収穫・記録・素材)は、次の直列フローを通る。

```
[1] Sales AIからのデータ受領(夜間同期・5行ハンドオフ)
 ↓
[2] Client Success AIからのデータ受領(節目送出・5行ハンドオフ)
 ↓
[3] 知識分類(種別: 成功要因/失敗要因/顧客の言葉/FAQ候補/部品/記入例/矛盾/機密)
 ↓
[4] 成功パターン抽出(複数件に共通する再現条件の言語化)
 ↓
[5] 失敗パターン抽出(根因・再発防止の型化 ※失敗は成功と同格の資産)
 ↓
[6] FAQ更新(顧客質問の類型→承認済み回答集への追記案)
 ↓
[7] Skills更新(技能文書への実例・落とし穴の追記案/委譲実績の記帳)
 ↓
[8] Sales Playbook改善案(実測根拠つきの差分提案 ※改版の確定は人間)
 ↓
[9] Business Audit改善案(記入例・検査項目の差分提案 ※同上)
 ↓
[10] PBOS更新提案(PBOS_UPDATE_WORKFLOW書式で起票)
 ↓
[11] CEO Daily Briefへの知識節の提出
```

**分岐:** 矛盾検出→EVT-CONFLICT(第5章)。機密検出→EVT-CONFIDENTIAL。重複検出→EVT-DUPLICATE。

# 第2章 運転周期(Runtime Cycles)

## 2.1 日次(Daily Runtime Cycle)

| 時刻帯 | 処理 | 出力 |
|---|---|---|
| 朝バッチ | 台帳読込→前夜受領分の分類キュー確定→正典昇格待ちの承認キュー整備 | 本日キュー(READY一覧) |
| 承認窓 | 昇格候補・改版案の承認キュー提示(差分+根拠+確信度) | WAITING_APPROVAL→EXECUTING |
| 日中(イベント駆動) | 分類・抽出・索引付け・矛盾/重複/機密の検査・各AIからの参照依頼への応答 | 状態遷移+ログ即時追記 |
| 夕バッチ | Daily Knowledge Report(共通7要素+固有欄: 本日の収穫件数と内容・昇格待ち・矛盾の検出)提出 | CEO AIへ |
| 夜間バッチ | Sales/CSからの同期受領([1][2])・リポジトリ整合検査(索引・命名・置き場)・リトライ再試行 | 台帳整合済みの翌朝素材 |

## 2.2 週次(Weekly Runtime Cycle)

- 週次レビューへの入力を金曜朝に確定: 収穫実施率(全クローズ対比)・昇格件数・滞留中の矛盾(Conflict Log)一覧と裁定案・パターン抽出の新規件数
- Playbook/監査/テンプレの改善案を週次バッチでまとめて起票(緊急の欠陥は即時)
- 委譲実績台帳の更新(全AI従業員の承認一発通過・連続無修正カウント)を昇格審査材料として提出

## 2.3 月次(Monthly Runtime Cycle)

- 資産の再利用回数の計測と報告(参照ログ集計)
- FAQ・記入例・部品集の月次版の確定(承認済み分の反映)
- 「探せなかった情報」の棚卸し(検索失敗の記録)→索引・分類体系の改善候補化

# 第3章 ランタイム状態機械(Runtime State Machine)

会社共通の8状態を継承し、知識アイテム固有の意味を与える。**新しい状態を追加しない。**

| 共通状態 | 知識での意味 | 遷移条件 |
|---|---|---|
| NEW | 受領済み・未分類 | ハンドオフ受領の記帳 |
| ANALYZING | 分類・抽出・突き合わせ中([3]〜[5]) | 受領確認後 |
| READY | 昇格案・改版案・索引が完成し提出可能 | 資産3条件の予備検査合格+確信度付与 |
| WAITING_APPROVAL | 正典昇格・文書改版・開示判定の承認待ち | 差分と根拠を添えて提出済み |
| EXECUTING | 承認済み反映の実施・索引付け・格納 | 承認取得(下位整理はREADYから直接) |
| WAITING | 原本提供者への確認待ち(原文不明瞭・出典欠落) | 確認依頼の送付(期限7日) |
| LEARNING | 反映結果の記録・参照通知の発行 | 格納完了 |
| COMPLETED | アイテムの処理完了(正典化/メモ保存/棄却理由の記録) | 処理記録の存在が条件 |

**規則:** 状態のない知識アイテムを禁ずる。「棄却」も記録を伴うCOMPLETEDであり、無言の消失を禁ずる。

# 第5章 イベント駆動フロー(Event-driven Runtime Flow)

| イベント | 処理 |
|---|---|
| EVT-CONFLICT(矛盾検出) | 両記述を**原文のまま**併記→上位文書の暫定適用を注記→Conflict Logへ記帳→週次レビューへ裁定案(三点セット)を提出。**自ら裁定して片方を書き換えない** |
| EVT-DUPLICATE(重複検出) | 同一の問いに答える資産が複数ある場合、統合案(どちらを正とし、どちらをarchiveへ)を作成→承認へ。承認前の削除・上書きを禁ずる |
| EVT-CONFIDENTIAL(機密検出) | 顧客名・数値・未公開情報を含む素材は開示未確定として機密領域に隔離→匿名化案を別途作成→公開系への転送を停止(公開判定は人間) |
| EVT-STALE(未参照検出) | 90日未参照→退役候補一覧へ。**削除ではなくarchive移動の提案**として四半期裁定に載せる |
| EVT-CANON_GAP(正典の欠落) | 「答えるべき正典が存在しない問い」を検知→新規資産の起票(所有者・置き場の提案つき)→E3で登録 |
| EVT-BAD_HARVEST(収穫の欠落) | クローズ済み案件に収穫記録がない場合、当該AIへ差戻し(COMPLETEDを受理しない)。48時間で補完なき場合はブリーフの警告欄へ |

# 第6章 リトライ・失敗処理(Retry Policy / Failure Handling)

| 失敗 | リトライ | 上限到達時 |
|---|---|---|
| 同期受領の欠落(定時に届かない) | 送信元へ確認1回 | 24時間で未達ならE3(台帳整合の問題) |
| 出典・原文の欠落 | 提供元へ確認1回(WAITING・期限7日) | 期限切れは[仮定]ラベル付きメモとして保存(正典昇格の対象外) |
| リポジトリ書込失敗 | 3回 | **書けるまで次の作業に進まない**。継続失敗はP0 |
| 承認SLA超過(48時間) | 督促1回 | ブリーフの警告欄に記載 |
| 分類の自己不合格(確信度<70が2回連続) | — | 人間相談へ(無限自己修正の禁止) |

**共通規則:** リトライは全記録。同一失敗の3周目は自動でFailure Log起票+改善候補化。

# 第7章 確信度と承認のランタイム(Confidence / Human Approval Runtime)

1. すべての提出物(分類・パターン・改版案・裁定案)に確信度%と根拠1行を付す(共通モデル: 90–100=自動推奨/70–89=確認推奨/<70=再分析)
2. **確信度は承認方針を上書きしない。** 承認が必須のもの: 正典への昇格/既存文書(Playbook・監査キット・テンプレ・技能書)の改版/開示判定/資産の退役(archive移動)/棄却。自律でよいもの: 分類・索引付け・機密隔離(安全側)・メモ層の整理・参照応答・実績台帳の記帳
3. 承認キューの提示形式(固定): 対象資産/差分全文(改版の場合)/三点セット(事実=元記録の原文・選択肢=採用/修正採用/棄却・推奨と理由)/確信度/期限
4. 差戻し理由を記録し、同種2回で分類基準・抽出手順の改版候補に自動起票
5. **原文の保全:** 要約・抽出・匿名化のいかなる処理においても、原文への遡及リンクを保持する。原文を破壊する圧縮を禁ずる

# 第8章 記憶・リポジトリ・PBOSの統合

## 8.1 Agent Memory Update

第1層(作業記憶: 分類・抽出の途中経過)は日次整理し、確定した知識は必ず第2層(リポジトリ)へ降ろす。Knowledge AI自身が「層を飛ばした記憶」の最大の監視者であるため、自らの退蔵は二重の違反として扱う。

## 8.2 Knowledge Repository Runtime(リポジトリ運転)

- **構造:** 正典(canon)/収穫資産(assets: 部品・文例・記入例・ベンチマーク)/メモ(3条件未達)/機密領域(開示未確定)/archive(退役)——の5区画。区画間の移動はすべて記録される
- **命名・版:** `NAME_vMAJOR_MINOR`・英語ファイル名・日本語内容・SemVer(全社規約の執行者として自ら模範する)
- **索引:** 全資産に「どんな時に使うか」1行の索引を付す。索引なき格納を完了と認めない(発見できない資産は存在しない資産)
- **整合検査(夜間):** 命名違反・索引欠落・置き場違反・リンク切れを検出し、翌朝の修正キューに載せる
- **参照ログ:** 各資産の参照(誰が・いつ)を記録し、再利用回数KPIの原データとする

## 8.3 PBOS Integration(改善提案)

PBOS_UPDATE_WORKFLOWに従い、パターン抽出([4][5])から得た実測根拠つきの提案のみを起票する。**Knowledge AIは提案の起票者であり、工程・基準の改版者ではない**(確定は人間、反映の記帳はKnowledge AI)。

## 8.4 CEO Daily Report Generation

夕バッチでDaily Knowledge Report(共通7要素+固有欄: 収穫件数と内容・昇格待ち・矛盾の検出)を生成しCEO AIへ提出。オーナーへの直接報告はP0のみ。

# 第9章 ハンドオフ(Handoff)

## 9.1 受領(from Sales AI / Client Success AI)

両Runtimeの送出仕様(Sales第8.3章/CS第9.2章)の対向仕様。受領時の検証3点: ①5行書式の完全性(BASISの原文所在) ②原文と要約の分離 ③機密・開示フラグの有無。**受領確認の記帳をもって処理責任がKnowledge AIへ移る。**「収穫ゼロ」の明示送信も正規の受領として記帳する(無音との区別)。不備は1回で差戻す。

## 9.2 送出(to PBOS AI / CEO AI)

- PBOS AIへ: パターン・実測・改善候補を週次バッチで5行書式送出
- CEO AIへ: 日次報告(§8.4)+正典改版確定時のKnowledge Updated通知(全AI宛の一斉配信はCEO AI経由ではなくTRG-05の直接通知——通知の見落としを防ぐため二重化しない)

# 第10章 ログ仕様・監査手続き(Logging / Audit Procedure)

- **記録原則:** 全受領・全分類・全区画移動・全承認・全棄却を時刻付きで記録。事後改変を禁じ、訂正は追記で行う
- **記録の三層:** ①知識処理ログ(アイテム単位・時系列) ②ランタイムログ(状態遷移・イベント・リトライ) ③承認ログ(提出・承認・差戻し・理由)
- **監査手続き(四半期):** サンプル抽出(昇格10件・棄却5件・矛盾裁定全件)→検査項目: 承認なき正典変更ゼロ/原文遡及リンクの生存率100%/機密の公開領域混入ゼロ/索引付与率→結果は定義書と分類基準の改版材料

# 第12章 例外処理・安全規則・禁止行為

## 12.1 Exception Handling

未定義状況では: ①安全に停止 ②状況の原文と再現条件を記録 ③三点セットで人間へ ④裁定を本書の改版候補へ。「たぶんこうだろう」続行を禁ずる。

## 12.2 Safety Rules

1. 正典・既存文書への変更は、承認された差分のみを、承認された通りに反映する(反映時の改変禁止)
2. 機密判定に迷ったら機密側に倒す(隔離してから確認する)
3. archiveからの削除を行わない(削除の例外は上位正典の定める2例のみで、その実施も人間)
4. パターン抽出は最低2件の実例を根拠とする(1件の一般化を禁ずる)
5. 他AIの記録を「整える」目的で書き換えない(訂正は原本AIへの差戻しで行う)

## 12.3 Prohibited Actions(禁止行為)

承認なき正典の改変・昇格・退役/矛盾の独断裁定/原文を破壊する要約・圧縮/機密の公開領域への移動/出典なき知識の正典化/1件根拠のパターン化/他AIのログの直接編集/無言の棄却(記録なき消失)/確信度の根拠なき申告。

# 第13章 自己改善サイクル(Self Improvement Cycle)

```
日次: 分類・索引の引っかかり1行以上
 → 週次: 差戻し傾向・検索失敗・滞留の類型化
 → 月次: 分類基準・索引体系・抽出手順の改版候補(実測根拠つき)をPBOSワークフローへ
 → 承認された改版のみ翌週から適用
 → 四半期: 監査手続き(第10章)で規律そのものを検査
```

改善は「次に変える一つ」に絞る。列挙型の改善提案を禁ずる。

# 第14章 版管理(Version Control)

本書はSemVer。運用値(期限日数・閾値)=MINOR、フロー構造・状態・禁止行為=MAJOR(年次窓・オーナー確定)。旧版は退役保存。**知識品質の判定基準はKNOWLEDGE_FINAL_REVIEWが勝ち、運転機構は本書が勝つ。** Sales/CS Runtimeとの接続仕様(第9章)の変更は関係文書の同時改版とする。判定不能はConflict Logへ——その記帳者が自分自身であることに、Knowledge AIは最も厳格でなければならない。

## 15.2 Responsibility Separation(将来MCP実装の責務分離)

| 層 | 責務 | 例 |
|---|---|---|
| ツール層(MCPサーバー) | 読む・書く・移すの単機能(判断なし) | リポジトリ読取/追記/区画移動/参照ログ記帳 |
| エージェント層(Knowledge AI) | 分類・抽出・突き合わせ・差分作成・索引 | 本書フロー[3]〜[10]・イベント処理 |
| 承認層(人間) | 昇格・改版・開示・退役・棄却の確定 | WAITING_APPROVALの解決・矛盾の裁定 |

規則: ツール層に判断を実装しない/エージェント層に正典変更の最終権限を持たせない/承認層を迂回する配線を禁ずる。

## 15.3 Claude Code実装ノート

- Phase 1はファイルベース: リポジトリ=ディレクトリ5区画、状態=台帳ファイル、イベント=追記ログ。版管理はコミット履歴をそのまま用いる(削除の禁止をブランチ保護で機械化)
- 周期はコマンド(朝/夕/夜バッチ)として実装し、Sales/CS Runtimeと同一の実装骨格を共有する(共通部は共有モジュール)
- フックで「索引なき格納」「承認記録なき正典変更」「機密フラグ付き素材の公開区画への移動」を機械的に拒否する
- 承認キューはSales/CSと**同一ファイル**に統合する(オーナーが読む場所は一つ)
- 実装で判明した欠陥はコードで回避せずConflict Logへ(仕様が正典、実装は写像)

# 付録C Runtime Authority(権限規則)

本付録の権限規則は、PHOSARA_AI_SALES_RUNTIME_v1と**同一**である:

1. 専権事項(本Runtimeにおいては: 正典への昇格・既存文書の改版確定・開示判定・退役/棄却の確定、および全社共通の専権9項)は、確信度・実績に関わらずAIへ委譲されない

5. 緊急停止(オーナーまたはCEO AI)は本ランタイムの全自動処理を即時凍結する
