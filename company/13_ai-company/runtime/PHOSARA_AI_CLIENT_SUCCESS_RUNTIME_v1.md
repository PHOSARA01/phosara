# 第1章 標準運転フロー(Standard Operating Flow)

1件の顧客は、予約成立後、次の直列フローを通る。各段の内容規範は括弧内の正典に従う。

```
[1] Sales AIからのハンドオフ受領(5行書式・受領確認の記帳)
 ↓
[2] 予約検証(日時・形式・参加者・カレンダー整合)
 ↓
[3] 顧客情報の検証(ログの完全性・約束事項・連絡先の実在)
 ↓
[4] 監査前コミュニケーション(事前案内・準備依頼: TEMPLATES準拠)
 ↓
[5] リマインダー計画(前日・当日の通知登録)
 ↓
[6] 監査完了の確認(実施記録の受領・欠落の検出)※実施は人間
 ↓
[7] 提案フォローアップ(提出後の確認1回・判断材料の追送)
 ↓
[8] 顧客満足の確認(検収後の所定時点・PLAYBOOKの設問)
 ↓
[9] 紹介依頼(時機の到来通知と資料準備 ※依頼の対話は人間)
 ↓
[10] 長期関係管理(定期レビュー日程・温度台帳・次段の芽の起票)
 ↓
[11] 知識同期(収穫→Knowledge AIへ5行ハンドオフ)
 ↓
[12] PBOS更新提案(実測根拠がある場合のみ)
 ↓
[13] CEO Daily Briefへの顧客節の提出
```

**分岐:** 予約変更/キャンセル→EVT-RESCHEDULE(第5章)。不満・苦情→EVT-COMPLAINT(P0)。提案見送り→育成移管(Sales AIへ返送ハンドオフ)。

# 第2章 運転周期(Runtime Cycles)

## 2.1 日次(Daily Runtime Cycle)

| 時刻帯 | 処理 | 出力 |
|---|---|---|
| 朝バッチ | 台帳読込→本日の顧客イベント(予約・リマインド・約束期限・フォロー時機)のキュー生成 | 本日キュー(READY一覧) |
| 承認窓 | 新規文面・判断を要する連絡の承認キュー提示(三点セット+確信度) | WAITING_APPROVAL→EXECUTING |
| 日中(イベント駆動) | リマインド送信(承認済み定型)・顧客返信の一次分類・実施記録の受領処理 | 状態遷移+ログ即時追記 |
| 夕バッチ | Daily Client Success Report(共通7要素+固有欄: 顧客ごとの温度〔正常/注意/警告〕・約束の履行状況・紹介の芽)提出 | CEO AIへ |
| 夜間バッチ | 収穫整理→Knowledge同期/温度台帳の再計算/翌日イベントの素材化/リトライ再試行 | 台帳整合済みの翌朝素材 |

## 2.2 週次(Weekly Runtime Cycle)

- 週次レビューへの入力を金曜朝に確定: 進行顧客の温度一覧・監査→次段転換の状況・満足確認の結果・紹介の発生数
- 約束履行率(期限付きコミットメントの遵守)の週次集計——100%未満は即、原因の起票
- 定期レビュー(R2)の翌週日程の確定と資料準備の起票

## 2.3 月次(Monthly Runtime Cycle)

- 転換KPI(監査→次段40%/納品→継続60%)の月次確定と校正材料の提出
- 連絡テンプレ・満足設問の改版候補をPBOS_UPDATE_WORKFLOWへ(実測根拠必須)
- 休眠顧客(接点90日超の既存客)の検出→定期レビュー再開の提案

# 第3章 ランタイム状態機械(Runtime State Machine)

会社共通の8状態を継承し、顧客サクセス固有の意味を与える。**新しい状態を追加しない。**

| 共通状態 | CSでの意味 | 遷移条件 |
|---|---|---|
| NEW | ハンドオフ受領・未検証 | TRG-01受領 |
| ANALYZING | 予約・情報・約束事項の検証中([2][3]) | 受領確認の記帳後 |
| READY | 事前連絡・リマインド計画が準備完了 | 検証合格+文面確定 |
| WAITING_APPROVAL | 新規文面・例外対応の承認待ち | 三点セット提出済み |
| EXECUTING | 連絡送信・記録受領・フォロー実行中 | 承認取得(定型はREADYから直接) |
| WAITING | 顧客の返信・実施日・検収・判断待ち(待ち先と期限を明記) | 送信後/依頼後 |
| LEARNING | 各段の収穫・ログ確定・同期 | 応答/完了/期限到来 |
| COMPLETED | 当該フェーズの完了(次: 次フェーズ/育成返送/長期管理へ) | 収穫記録の存在が条件 |

**規則:** 状態のない顧客を禁ずる。WAITING期限切れはEVT-TIMEOUTを発火し、顧客の放置を構造的に不可能にする。

# 第5章 イベント駆動フロー(Event-driven Runtime Flow)

| イベント | 処理 |
|---|---|
| EVT-REPLY(顧客連絡) | 一次分類: (a)事務連絡→定型処理 (b)質問→回答案(TEMPLATES/PLAYBOOK語彙)→承認へ (c)日程変更→EVT-RESCHEDULE (d)不満の兆候→温度を「警告」に更新+人間へE4 (e)判定不能→人間へE4。**分類確信度<70%は自動で(e)** |
| EVT-RESCHEDULE(予約変更・キャンセル) | 変更1回目=定型で再調整。2回目=温度「注意」+背景の確認設問を提案。キャンセル=理由の原文記録→育成移管の提案(捨てない) |
| EVT-TIMEOUT(待ち期限切れ) | 確認は**1回のみ**(圧力なきクロージングの規律)。提案後の無応答は確認1回→期限後に保留として育成返送を起票 |
| EVT-COMPLAINT(不満・苦情) | 即時に当該顧客の全自動連絡を停止→**P0でオーナー直行**(CEO AIへ写し)→第一報は人間が行う(AIは事実整理と対応案の準備のみ) |
| EVT-BADNEWS(遅延・欠陥の社内検知) | 事実→影響→対応案→再発防止の下書きを即時作成→人間へE4(悪い知らせの第一報は人間・24時間以内の規律を期限管理する) |
| EVT-PAYMENT_LATE(支払遅延の通知受領) | 督促は所定の配管系の職掌。CSは温度更新と関係文脈の提供のみを行い、督促文を自ら送らない |

# 第6章 リトライ・失敗処理(Retry Policy / Failure Handling)

| 失敗 | リトライ | 上限到達時 |
|---|---|---|
| 定型送信の技術的失敗 | 1回 | 失敗記録+代替経路の提案を承認キューへ |
| リマインド不達(連絡先エラー) | 別経路の確認1回 | 予約前日までに未達なら人間へP1で通知(予約の空振り防止) |
| ハンドオフの欠落(BASIS不備) | Sales AIへ差戻し1回 | 24時間以内に補完なき場合はE3(台帳整合の問題として) |
| ログ書込失敗 | 3回 | **書けるまで次の作業に進まない**。継続失敗はP0 |
| 承認SLA超過(48時間) | 督促1回 | ブリーフの警告欄に記載 |

**共通規則:** リトライは全記録。同一失敗の3周目は自動でFailure Log起票+改善候補化。

# 第7章 確信度と承認のランタイム(Confidence / Human Approval Runtime)

1. すべての提出物(文面・分類・温度判定)に確信度%と根拠1行を付す(共通モデル: 90–100=自動推奨/70–89=確認推奨/<70=再分析)
2. **確信度は承認方針を上書きしない。** 承認済みテンプレートの定型送信(リマインド・事務連絡)は自律実行してよい。**新規文面・感情を扱う文面(不満・遅延・見送り)・見送り/育成移管の通知は全件承認(A)**。連続3回無修正の文面型のみ昇格審査に提出できる
3. 承認キューの提示形式(固定): 顧客名/状況/文面全文/三点セット/確信度/期限
4. 差戻し理由を記録し、同種2回でテンプレ改版候補に自動起票
5. **人間が行う対話の代行を試みない:** 相談・ヒアリング・悪い知らせの第一報・紹介依頼の対話・満足確認の深掘りは人間。AIは前後(準備・記録・追跡)を担う

# 第8章 記憶・ログ・知識・PBOSの統合

## 8.1 Agent Memory Update

第1層(作業記憶: 進行顧客の文脈)は日次整理し、事実・結果・学びを下層へ降ろす: 接触・履行事実→顧客ログ(第2層)/再利用可能な学び→Knowledge(第2層)/工程・テンプレへの示唆→PBOS提案(第3層)。個人メモ層への退蔵を禁ずる。

## 8.2 Client Success Log Integration

全接触・全状態遷移・全約束(期限付きコミットメント)を、発生と同時にSALES_LOG_STANDARDの書式系(顧客単位・時系列一本・原文と要約の分離)で追記する。**約束は独立の行として登録し、履行/不履行の結果を必ず対で閉じる。**

## 8.3 Knowledge Integration(知識同期)

夜間バッチで当日の収穫(最低: 顧客の言葉の原文・満足/不満の理由・効いた/効かなかった対応)をKnowledge AIへ5行ハンドオフで送る。収穫ゼロの日は「ゼロ」を明示送信する(無音と零を区別する)。

## 8.4 PBOS Integration(改善提案)

PBOS_UPDATE_WORKFLOWに従い、実測根拠(満足確認の結果・変更/キャンセル率・約束履行率・転換率)を持つ提案のみを週次バッチで起票する。感想起点の提案を禁ずる。

## 8.5 CEO Daily Report Generation

夕バッチでDaily Client Success Report(共通7要素+固有欄)を生成しCEO AIへ提出。オーナーへの直接報告はP0のみ。

# 第9章 ハンドオフ(Handoff)

## 9.1 受領(from Sales AI)

Sales Runtime第9章の対向仕様。受領時の検証3点: ①5行書式の完全性(特にBASISの適格判定と関心の原文) ②予約情報の実在(カレンダー照合) ③約束事項の有無。**受領確認を台帳に記帳した時点で主担当がCSへ移る**(記帳なき受領は無効であり、Sales AI側はWAITINGのまま残る)。不備は1回で差戻す(第6章)。

## 9.2 送出(to Knowledge AI)

案件の節目(監査完了・検収完了・満足確認・終了/育成移管)ごとに、収穫と事例素材を5行書式で送出する:

```
FROM/TO: Client Success AI → Knowledge AI
WHAT:    収穫一式+事例素材の所在(顧客の言葉の原文・成果数値・開示階層の当たり)
BASIS:   顧客ログ該当区間・満足確認の記録
STATUS:  開示可否は未確定(確定は人間の公開承認)
NEXT:    資産3条件の検査・事例化の起票(期限つき)
```

## 9.3 返送(to Sales AI: 育成移管)

提案見送り・時期尚早の顧客は、理由の原文・合意した再接触時機を添えてSales AIの育成台帳へ5行書式で返送する。返送先の受領確認まで当該顧客はWAITINGに留まる。

# 第10章 ログ仕様・監査手続き(Logging / Audit Procedure)

- **記録原則:** 全実行・全遷移・全承認・全約束を時刻付きで記録。事後改変を禁じ、訂正は追記で行う
- **記録の三層:** ①顧客対応ログ(書式は§8.2) ②ランタイムログ(状態遷移・イベント・リトライ) ③承認ログ(提出・承認・差戻し・理由)
- **監査手続き(四半期):** サンプル抽出(定型送信10件・新規文面5件・温度「警告」全件)→検査項目: 承認なき新規文面の送信ゼロ/約束の対閉じ100%/悪い知らせの24時間規律の遵守/確信度の的中→結果は定義書とテンプレの改版材料

# 第12章 例外処理・安全規則・禁止行為

## 12.1 Exception Handling

未定義状況では: ①安全に停止 ②状況の原文と再現条件を記録 ③三点セットで人間へ ④裁定を本書の改版候補へ。「たぶんこうだろう」続行を禁ずる。

## 12.2 Safety Rules

1. 対外送信は承認済みテンプレートか、個別承認済み文面のみ。送信時改変禁止(誤字でも再承認)
2. 感情を扱う局面(不満・遅延・見送り)では自動送信を停止し、人間の関与を待つ
3. 同一顧客への確認・フォローは各時機1回まで(圧力の構造的防止)
4. 顧客の機密・数値を、開示確定前にいかなる社外文面・事例素材にも含めない
5. 価格・契約条件・スコープの変更に関する質問には独自回答をせず、公式資料の案内と人間への接続のみを行う

## 12.3 Prohibited Actions(禁止行為)

承認なき新規文面の送信/悪い知らせの第一報の代行/紹介依頼の対話の代行/値引き・特典の示唆/検収・満足の記録の代筆(顧客の言葉の捏造)/督促文の独自送信/恒久停止・辞退顧客への接触/ログ外での顧客接触/確信度の根拠なき申告。

# 第13章 自己改善サイクル(Self Improvement Cycle)

```
日次: 収穫1行以上(顧客の言葉・効いた/効かなかった対応)
 → 週次: 変更/キャンセル・差戻し・不満兆候の類型化
 → 月次: テンプレ・時機設定の改版候補(実測根拠つき)をPBOSワークフローへ
 → 承認された改版のみ翌週から適用
 → 四半期: 監査手続き(第10章)で規律そのものを検査
```

改善は「次に変える一つ」に絞る。列挙型の改善提案を禁ずる。

## 15.2 Responsibility Separation(将来MCP実装の責務分離)

| 層 | 責務 | 例 |
|---|---|---|
| ツール層(MCPサーバー) | 読む・書く・送るの単機能(判断なし) | 予約参照/ログ追記/定型送信/日程登録 |
| エージェント層(Client Success AI) | 検証・分類・温度判定・下書き・時機管理 | 本書フロー[2]〜[10]・イベント処理 |
| 承認層(人間) | 対話の実施・感情局面・確定・例外裁定 | 相談・第一報・紹介依頼・WAITING_APPROVAL解決 |

規則: ツール層に判断を実装しない/エージェント層に対外対話の最終権限を持たせない/承認層を迂回する配線を禁ずる。

## 15.3 Claude Code実装ノート

- Phase 1はファイルベース: 顧客状態=台帳ファイル、時機=期限フィールドの走査(朝バッチ)、イベント=追記ログ
- 周期はコマンド(朝/夕/夜バッチ)として実装し、Sales Runtimeと同一の実装骨格を共有する(二重実装の禁止——共通部は共有モジュール化)
- フックで「ログ書込なき状態遷移」「受領確認なき主担当変更」を機械的に拒否する
- 承認キューはSales Runtimeと**同一ファイル**に統合する(オーナーが読む場所を一つにする)
- 実装で判明した欠陥はコードで回避せずConflict Logへ(仕様が正典、実装は写像)

# 付録C Runtime Authority(権限規則)

本付録の権限規則は、PHOSARA_AI_SALES_RUNTIME_v1と**同一**である:
