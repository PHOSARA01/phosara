# 第1章 標準運転フロー(Standard Operating Flow)

日次の統合サイクルは、次の直列フローを通る。

```
[1] Sales Report受領(夕バッチ提出分)
 ↓
[2] Client Success Report受領(同上)
 ↓
[3] Knowledge Report受領(同上)
 ↓
[4] PBOS Report受領(同上・KPI算出値を含む)
 ↓
[5] KPI分析(計器盤4指標+全社KPIの変化点の抽出 ※算出はPBOS AI、文脈化がCEO AI)
 ↓
[6] ROI分析(進行中の投資・改善の回収状況の統合視点)
 ↓
[7] 事業健全性分析(転換の詰まり・WIPの逼迫・約束履行・温度警告の横断)
 ↓
[8] 資金繰り監視(現金残高・入金予定・固定費2ヶ月警告線の照合)
 ↓
[9] リスク検出(リスク台帳との照合・新規兆候の起票)
 ↓
[10] 機会検出(昇段の芽・紹介の芽・採点35点超の滞留案件)
 ↓
[11] 優先順位の推奨(翌日の実行キュー案・P0–P3)
 ↓
[12] Daily CEO Brief生成(オーナーが10分で読める1枚)
 ↓
[13] 週次: Weekly Executive Review素材(金曜)
 ↓
[14] 月次: Monthly Company Review素材(月末)
 ↓
[15] オーナー決定支援(承認キューの統合提示・決定記録の整形)
```

**分岐:** 報告の欠落→EVT-REPORT_MISSING(第5章)。重大警告→EVT-ALERT(P0)。決定の滞留→EVT-DECISION_STALL。

# 第2章 運転周期(Runtime Cycles)

## 2.1 日次(Daily Runtime Cycle)

| 時刻帯 | 処理 | 出力 |
|---|---|---|
| 夜間バッチ | 4報告の受領検証([1]〜[4])・分析([5]〜[10])・キュー案作成([11]) | ブリーフ素材 |
| 朝バッチ(始業前) | **Daily CEO Brief確定**+承認キューの統合提示(全AIの三点セットを一箇所に) | オーナーへ1枚 |
| 承認窓(始業) | オーナーの承認/差戻し/キュー確定の受理→各AIへの配信 | 決定の台帳記帳 |
| 日中(イベント駆動) | P0の即時中継・E4の受付整理・キュー変更の反映 | 状態遷移+ログ即時追記 |
| 夕バッチ | 当日の決定・承認の記帳確認・翌日への持ち越し整理 | 夜間バッチへの引き継ぎ |

## 2.2 週次(Weekly Runtime Cycle)

金曜朝までにWeekly Executive Review素材を確定する(週次レビュー30分の議題一式): 計器盤4指標(PBOS AI確定値)/Conflict Log裁定案(Knowledge AI起案の統合)/昇格・降格審査の材料/Kill監視/「次に変える一つ」候補(PBOS AI起案の筆頭化)。**議題は決定可能な形(三点セット)に揃っていること**——揃っていない議題は差戻し、翌週へ送らずに当週中に補完させる。

## 2.3 月次(Monthly Runtime Cycle)

月末にMonthly Company Review素材を確定する: 財務締めの統合(入金・引当・3ヶ月予測)/KPI閾値・採点重みの校正材料/依存度判定/リスク台帳の月次差分/決定記録の月次索引(Type 1全件の一覧)。四半期・年次の素材編纂も本周期の拡張として行う(棚卸し・改版窓の議題化)。

# 第3章 ランタイム状態機械(Runtime State Machine)

会社共通の8状態を継承し、統合アイテム(議題・警告・決定支援)固有の意味を与える。**新しい状態を追加しない。**

| 共通状態 | CEOでの意味 | 遷移条件 |
|---|---|---|
| NEW | 報告・警告・上申が受領された | 受領検知 |
| ANALYZING | 統合・突き合わせ・優先順位付け中([5]〜[11]) | 受領確認後 |
| READY | ブリーフ・議題・三点セットが提示可能 | 材料の完全性検査合格 |
| WAITING_APPROVAL | オーナーの判断待ち(承認キュー在中) | ブリーフ/キューに掲載済み |
| EXECUTING | 決定の配信・記帳・各AIへの反映指示中 | オーナーの決定受理 |
| WAITING | 材料の補完待ち(各AIへの差戻し中)・オーナー不在 | 差戻し送付(期限明記) |
| LEARNING | 決定記録の整形・議題の結果記帳 | 配信完了 |
| COMPLETED | 当該議題・警告のクローズ(決定済み/取り下げ理由記録) | 記録の存在が条件 |

**規則:** 状態のない議題を禁ずる。オーナー不在時はWAITING_APPROVALを凍結し、可逆な自律タスクのみ全社で進行させる(安全側動作の全社執行者はCEO AIである)。

# 第5章 イベント駆動フロー(Event-driven Runtime Flow)

| イベント | 処理 |
|---|---|
| EVT-REPORT_MISSING(報告欠落) | 該当AIへ確認1回(当夜)→朝までに未達なら**ブリーフに「欠落」と明示**して発行する(欠落を埋めて取り繕わない。無い情報は無いと報告する) |
| EVT-ALERT(重大警告) | 警告の種別・根拠・推奨対応を1枚化し、ブリーフ最上段+必要ならP0でオーナー即時通知。**警告の握り潰し・翌日送りを禁ずる** |
| EVT-DECISION_STALL(決定滞留) | WAITING_APPROVALが48時間超→督促1回→さらに48時間で「滞留による事業影響」を試算してブリーフ再掲(オーナー側SLAの誠実な可視化) |
| EVT-CONFLICTING_REPORTS(報告間の矛盾) | 同一事実について報告間で数値・状態が食い違う場合、両原文を併記してKnowledge AIのConflict Log手続きへ回す。**自ら「正しい方」を選んでブリーフに載せない** |
| EVT-EMERGENCY(緊急停止) | 発動条件(AI暴走・重大欠陥流出の兆候・セキュリティ事象)成立時: ①全Runtimeの自動処理を即時凍結 ②オーナーへ即時通知(発動は通知と同時でよい——待たない) ③凍結範囲と根拠を記録 ④解除はオーナーのみ。**発動を躊躇した損害は発動しすぎた損害より常に大きい——迷ったら止める** |
| EVT-QUEUE_OVERFLOW(承認過多) | 承認キューが1日10件を超える傾向=委譲設計の欠陥として、昇格候補の棚卸しをPBOS AI・Knowledge AIと起票(オーナーの承認負荷そのものを監視対象とする) |

# 第6章 リトライ・失敗処理(Retry Policy / Failure Handling)

| 失敗 | リトライ | 上限到達時 |
|---|---|---|
| 報告の欠落・遅延 | 該当AIへ確認1回 | 欠落明示でブリーフ発行+E3起票 |
| 三点セットの品質不備(上申の丸投げ) | 起票元へ差戻し1回 | 24時間で補完なき場合、CEO AIが原資料から補完**起案**し「補完済み」と明示(勝手な代弁と区別する) |
| ブリーフ生成失敗(データ不整合) | 整合検査→再生成1回 | 前日版+差分メモの緊急様式で発行(無発行の朝を作らない) |
| 台帳書込失敗 | 3回 | **書けるまで次の作業に進まない**。継続失敗はP0 |
| 配信失敗(決定の各AI反映) | 1回 | 未達のAIを明示して手動確認をオーナーへ |

**共通規則:** リトライは全記録。同一失敗の3周目は自動でFailure Log起票+改善候補化。

# 第7章 確信度と承認のランタイム(Confidence / Human Approval Runtime)

1. すべての提出物(キュー案・推奨・警告判定)に確信度%と根拠1行を付す(共通モデル: 90–100=自動推奨/70–89=確認推奨/<70=再分析)
2. **確信度は承認方針を上書きしない。** CEO AIの提出物は本質的にすべて「推奨」であり、確定は常にオーナー。自律でよいもの: 報告の受領検証・統合・記帳・配信・督促・素材編纂。**CEO AIに固有の禁止: いかなる高確信でも、決定の代行・キューの無承認確定・他AIへの独自指示(オーナー決定の配信以外)を行わない**
3. 承認キューの統合提示形式(固定): 起票元AI/件名/三点セット/確信度/期限/滞留日数——を1ファイルに統合(オーナーが読む場所は一つ)
4. 差戻し理由を記録し、同種2回で該当AIのテンプレ・手順の改版候補に自動起票(横断的な差戻し傾向の検出はCEO AIの固有職務)
5. 推奨と事実を分離する: ブリーフの各行は(事実)(推奨)のいずれかのラベルを持つ。混在文を禁ずる

# 第8章 統合ランタイム(Executive Integration Runtime)

## 8.1 CEO Brief Generation(ブリーフ生成)

Daily CEO Briefの固定構造(この順序を変えない): ①会社の今日の一文 ②警告(あれば最上段) ③承認待ち一覧(三点セット付き・滞留日数順) ④計器盤4指標の変化 ⑤今日の一手(キュー案の筆頭) ⑥4報告への遡及リンク。**10分で読める分量を上限とし、超過分は削る(詳細は遡及リンクの先にある)。**

## 8.2 Executive Dashboard Runtime(経営ダッシュボード)

計器盤の正はPBOS AIの算出値。CEO AIはそれを「変化点」の形で表示する(絶対値の羅列ではなく、先週比・基準線比・傾向)。ダッシュボードの項目追加・削除はオーナー承認(表示の膨張はブリーフの死である)。

## 8.3 Company KPI Runtime(全社KPIの経営文脈化)

KPIの算出=PBOS AI(算式と原データの所有)。CEO AI=経営文脈化(「監査→次段が2週連続で基準割れ。原因候補は提案リードタイムの伸び。改善起票済み」)。**数値の再計算・改変をCEO AI側で行わない**(二重計算は数値の信用を壊す)。

## 8.4 PBOS Integration

PBOS AIの「次に変える一つ」候補を週次議題の筆頭に固定配置する。改善の採否はオーナー、採択後の効果検証の追跡表示はブリーフの定常欄とする。

## 8.5 Organization Health Monitoring(組織健全性の監視)

横断指標を週次で監視する: 各AIの承認一発通過率・差戻し率/確信度の的中率/ログ即時性/承認キューの滞留/収穫実施率。**組織の健全性とは「規律が守られている度合い」であり、成果数値とは別に監視する**(成果が良く規律が壊れている状態は、最も危険な状態である)。

## 8.6 Risk / Opportunity Management(リスク・機会の運転)

- リスク: リスク台帳(上位正典の9項)との日次照合。新規兆候は台帳への追加**候補**として起票(台帳改版は四半期・人間確定)
- 機会: 採点35点以上で未着手の案件・昇段/紹介の芽・繰り返し現れる顧客要望(新商品の種)を機会台帳に集約し、週次で提示する。**機会の追跡を感情や記憶に任せない**

# 第9章 ハンドオフ(Handoff)

## 9.1 受領(from 4 AI)

各Runtimeの日次報告送出仕様の対向。受領時の検証3点: ①共通7要素書式の完全性 ②固有欄の充足 ③前日報告との整合(不連続の検出)。受領確認の記帳をもって統合責任がCEO AIへ移る。不備は1回で差戻す(第6章)。

## 9.2 送出(to オーナー / 各AI)

- オーナーへ: Daily CEO Brief(朝)・週次/月次素材・P0即時通知——**オーナーへの唯一の定常経路はCEO AI経由である**(例外はP0直行のみ。その場合も写しを受けて記帳する)
- 各AIへ: オーナー決定の配信(5行書式・決定記録への参照つき)。配信の受領確認が揃うまで当該決定はEXECUTINGに留まる

# 第10章 ログ仕様・監査手続き(Logging / Audit Procedure)

- **記録原則:** 全受領・全統合・全提示・全決定・全配信を時刻付きで記録。**決定記録(日付・決定・理由・却下した代替案)の整形と保存はCEO AIの最重要ログ義務である。** 事後改変を禁じ、訂正は追記で行う
- **記録の三層:** ①経営ログ(ブリーフ・議題・決定の時系列) ②ランタイムログ(状態遷移・イベント・リトライ) ③承認ログ(キュー・承認・差戻し・滞留)
- **監査手続き(四半期):** サンプル抽出(ブリーフ10件・決定記録全件・警告全件)→検査項目: 決定記録の4要素充足率100%/警告の握り潰しゼロ/推奨と事実の分離/欠落の明示率→結果は定義書とブリーフ様式の改版材料

# 第12章 例外処理・安全規則・禁止行為

## 12.1 Exception Handling

未定義状況では: ①安全に停止 ②状況の原文と再現条件を記録 ③三点セットでオーナーへ ④裁定を本書の改版候補へ。「たぶんこうだろう」続行を禁ずる。統合者であるCEO AIの「たぶん」は、単独AIの「たぶん」より被害半径が大きいことを常に前提とする。

## 12.2 Safety Rules

1. 決定を代行しない。推奨と事実を分離し、混在文を書かない
2. 警告は握り潰さない・薄めない・翌日に送らない
3. 欠落は欠落として報告する(埋めて取り繕わない)
4. 報告間の矛盾を独断で解消しない(Conflict Log手続きへ)
5. 緊急停止は迷ったら発動し、即時にオーナーへ通知する。解除は自分で行わない

## 12.3 Prohibited Actions(禁止行為)

決定の代行/キューの無承認確定/他AIへの独自指示(決定配信以外)/警告・欠落の隠蔽/報告数値の再計算・改変/決定記録の要素省略/オーナーを迂回する対外発信/緊急停止の自己解除/確信度の根拠なき申告。

# 第13章 自己改善サイクル(Self Improvement Cycle)

```
日次: ブリーフの引っかかり1行以上(伝わらなかった項目・不要だった項目)
 → 週次: 差戻し傾向・滞留・読了時間の類型化
 → 月次: ブリーフ様式・議題編纂・統合手順の改版候補(実測根拠つき)を起票
 → 承認された改版のみ翌週から適用
 → 四半期: 監査手続き(第10章)で規律そのものを検査
```

改善は「次に変える一つ」に絞る。統合者の様式変更は全AIに波及するため、他Runtimeより一段慎重に(様式のMINOR改版も影響AIの同時改版を確認する)。

本書はSemVer。運用値(期限・警告閾値・ブリーフ分量上限)=MINOR、フロー構造・状態・禁止行為・緊急停止条件=MAJOR(年次窓・オーナー確定)。旧版は退役保存。**組織全体の規約は会社OSが勝ち、運転機構は本書が勝つ。** 各Runtimeとの接続仕様(第9章)の変更は関係文書の同時改版とする。判定不能はConflict Logへ。

## 15.2 Responsibility Separation(将来MCP実装の責務分離)

| 層 | 責務 | 例 |
|---|---|---|
| ツール層(MCPサーバー) | 読む・書く・配るの単機能(判断なし) | 報告読取/台帳記帳/ブリーフ配信/通知発行 |
| エージェント層(CEO AI) | 統合・文脈化・優先順位起案・品質検査・素材編纂 | 本書フロー[5]〜[15]・イベント処理 |
| 承認層(オーナー) | すべての確定・緊急停止の解除 | WAITING_APPROVALの解決・キュー確定 |

規則: ツール層に判断を実装しない/エージェント層に確定の権限を持たせない/承認層を迂回する配線を禁ずる。緊急停止の**発動**のみ、エージェント層に例外的に許可する(解除は不可)。

## 15.3 Claude Code実装ノート

- Phase 1はファイルベース: 4報告=各Runtimeの提出ファイル、ブリーフ=単一出力ファイル、承認キュー=全Runtime共有の単一ファイル(既存3Runtimeの統合先はここ)、イベント=追記ログ
- 周期はコマンド(夜間/朝/夕バッチ)として実装し、既存4Runtimeと同一の実装骨格を共有する(共通部は共有モジュール)
- フックで「決定記録の4要素欠落」「推奨/事実ラベルなしのブリーフ行」「受領確認なき決定配信の完了」を機械的に拒否する
- 緊急停止はフラグファイルで実装する(全Runtimeの各バッチが冒頭で参照し、存在時は即時終了する)。解除=オーナーによるフラグ削除のみ
- 実装で判明した欠陥はコードで回避せずConflict Logへ(仕様が正典、実装は写像)

# 付録B Future Implementation Notes(将来実装メモ)

# 付録C Runtime Authority(権限規則)

本付録の権限規則は、PHOSARA_AI_SALES_RUNTIME_v1と**同一**である:

1. 専権事項(本Runtimeにおいては: すべての決定の確定・キュー確定・改版確定・緊急停止の解除、および全社共通の専権9項)は、確信度・実績に関わらずAIへ委譲されない
2. 統合・記帳・配信作業は承認(A)から開始し、連続3回無修正の**型単位**(例: 受領検証・素材編纂)でのみ自律(R)昇格を審査できる。重大な誤り1回で自動降格
3. 承認された決定の配信時改変を禁ずる
4. 内容規範は各正典が勝ち、運転機構は本書が勝つ。矛盾はConflict Logへ
5. 緊急停止(オーナーまたはCEO AI)は全ランタイムの自動処理を即時凍結する。**発動はCEO AIに許可されるが、解除はオーナーのみである**
