# SKILLS.md — スキルの蓄積と昇格

**スキルとは:** 再現可能な手順として文書化され、Claude Codeがそのまま実行できる状態になった「凍結された成功」。ワークフロー(WORKFLOW.md)が「何をすべきか」なら、スキルは「過去にうまくいった正確なやり方」である。
**思想:** 一度解いた問題は二度と手作業で解かない(Company OS V3)。スキルはPHOSARAの複利の単位であり、60日後に残る最重要資産のひとつ。

---

## 1. 昇格ライン(手作業→スキル)

```
手作業(1回目: logs/success/に記録)
→ 手順メモ(2回目: 前回ログを見ながら実施し、差分を追記)
→ スキル候補(3回目: 同じ手順で安定成功 → AG-6が昇格を提案)
→ SKILL.md化(人間が承認 → skills/{name}/SKILL.md 作成)
→ 改訂(使用のたびに気づきを追記。3回連続で修正なしなら「安定」マーク)
```

**昇格基準(3条件AND):** ①3回以上の成功実績がログにある ②手順が汎用化できる(特定顧客の事情に依存しない)③次の60日でも使う見込みがある(最終判断ルール条件2)。

## 2. SKILL.mdの標準形式

```markdown
# SKILL: {スキル名}
- 状態: 候補 / 承認済 / 安定
- 昇格日: YYYY-MM-DD(根拠ログ: logs/success/xxx, yyy, zzz)
- 担当エージェント: AG-x
- 承認点: (このスキル実行中に人間承認が必要な地点)

## 目的(1行)
## 前提条件(入力・必要ファイル)
## 手順(番号付き。コマンド・プロンプト・テンプレはそのまま貼る)
## 検証(VERIFICATION.mdのどのチェックリストを通すか)
## 出力(何がどこに生成されるか)
## 既知の落とし穴(失敗ログから転記)
## 改訂履歴
```

## 3. 初期スキル候補(Phase Aで種を蒔き、実績とともに昇格させる)

| 候補名 | 元WF | 内容 | 昇格見込み |
|---|---|---|---|
| audit-tech-scan | WF-04 | Webサイト技術監査の自動計測(速度/モバイル/SEO基礎/リンク)→テンプレ転記 | Phase C(監査2件後) |
| audit-report-gen | WF-04 | 記入済みテンプレ→報告書ドラフト生成パイプライン | Phase C |
| outreach-draft | WF-01 | 下調べ→固有の観察1点入り接触文面の生成 | Phase B(接触15件後) |
| consult-prep | WF-03 | 相談準備パッケージ(下調べ+論点仮説+問い3つ)の生成 | Phase B |
| proposal-assemble | WF-05 | 監査報告書+価格表→提案書ドラフトの組立 | Phase D |
| wp-site-setup | WF-06 | WordPress環境の定型セットアップ | 初回制作後 |
| weekly-harvest | WF-08 | 週次収穫レビューの実施手順 | Day 21(3週目) |
| case-study-gen | WF-09 | 収穫素材→事例記事ドラフト(課題→診断→方向→結果) | Client Zero事例の公開後 |
| morning-brief | 共通 | STATE.md読込→当日タスク提案→最終判断ルール選別(/morningコマンド) | Day 10 |

**注意:** これは「先に作る」リストではない。**実績が3回溜まったものから昇格させる。** 実績なしにスキルを書くのは、標準化されていない業務の自動化(禁止事項)と同じ誤りである。

## 4. スキルの置き場と使い方

- 置き場: `skills/{skill-name}/SKILL.md`(必要な補助ファイルは同フォルダに)
- Claude Codeは該当作業の前に必ず関連SKILL.mdを読み込む(Explore工程に組込み)
- Claude Code製品のスキル機能へ実装する場合も、**正本はこのリポジトリのMarkdown**とし、製品形式へは変換して供給する(実行層の可搬性規律——Company OS改善仕様I-06)

## 5. スキルの廃棄

3ヶ月使われなかったスキルはAG-6が「休眠」フラグを提案する。削除はせず `skills/_archive/` へ移動(知識は捨てない、現役から外すだけ)。
