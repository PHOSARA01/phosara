# 第0章 位置づけ — HQ Coreへの接続宣言

## 0.1 本書の役割

HQ Core以前の文書群は「PHOSARAが**どう考えるか**」を定めた。本書は「PHOSARAが**どう働くか**」を定める。

本書は、HQ Coreの次の箇所の**実装仕様**である。新しい概念は導入せず、既存の概念を動く機構に落とす。

| HQ Coreの箇所 | 本書での実装 |
|---|---|
| §2.3 三つのフロー(情報・意思決定・資産) | 第1部の配線図・第4部の還流規則 |
| §5.3 統合アダプタ仕様(役割・接続面・不変条件) | 第1部の実行仕様(責務・入出力・トリガー・承認点) |
| 第3部 13エージェント編成 | 第2部の各工程への責任割当(A-01〜A-13) |
| §1.7 委譲レベルH/A/R・昇格ライン | 第3部ロードマップの推進エンジン |
| §1.4 機会スコアリング(R×3/A×3) | 第5部の実装優先順位の採点系 |
| 収穫の儀・資産3条件(§1.1 PBOS Rule) | 第4部の資産変換規則 |

## 0.2 遵守する不変条件(本書全体に適用)

1. **H領域の永久保持:** ヒアリング実施・スコア確定・優先課題確定・価格確定+HQ Core §1.8の全9項は、いかなる自動化フェーズでも人間が行う。**配管はH点を迂回しない**(HQ Core §5.3不変条件の再確認)
2. **STATE経由の原則:** すべての自動化・すべてのエージェントは、STATEを読んでから動き、STATEに書いて終わる。ハンドオフはHQ Core §3.14の5行書式
3. **教義とツールの分離:** 本書のうちツール名を含む箇所(第1部・第5部)は交換可能層である。工程・基準・還流規則(第2部・第4部)はツールが変わっても不変
4. **正典はGitHub:** 本書を含む全産物の正はGitリポジトリにあり、PRが改版の審査単位である

## 0.3 正典マップへの追記(HQ Core §0.2との整合)

| 問いの種類 | 正典 |
|---|---|
| **自動化の配線・トリガー・実行工程の機構・自動化の優先順位** | **本書(PHOSARA_EXECUTION_OS_v1_0)** |
| 日々の実行手順の詳細(9ワークフロー本文) | WORKFLOW.md(本書はこれを置換しない。工程IDで参照する) |

矛盾を発見した場合はHQ Core §0.3の手順(Conflict Log→上位暫定適用→週次裁定→最小修正)に従う。

# 第2部 Execution Workflow(実行ワークフロー)

## 2.1 PBOSステージとの対応(再設計ではなく直列表示)

本章の12工程(EX-01〜EX-12)は、PBOS 17ステージの**顧客一件が通る道筋を直列に表示したもの**である。PBOSを置換しない。育成(N1)・需要創出(D1)は本流の外周として常時回る。

| 実行工程 | PBOS該当 | 実行工程 | PBOS該当 |
|---|---|---|---|
| EX-01 リード | D1–D2/Q1–Q2 | EX-07 レビュー | B2 |
| EX-02 事業監査 | A1–A3 | EX-08 納品 | B3(→R1接続) |
| EX-03 提案 | P1 | EX-09 事例化 | H2 |
| EX-04 見積 | P1(価格内訳) | EX-10 紹介 | H3 |
| EX-05 契約 | P2 | EX-11 知識更新 | H1(総括収穫) |
| EX-06 制作 | B1 | EX-12 PBOS改善 | 改善ループ |

**収穫に関する整合(重要):** HQ Coreの原則により、収穫(H1)は**全工程の出口で毎回行う**。EX-11は各工程で発生した収穫物を**総括・正典化する統合点**であり、「最後にまとめて収穫する」という意味ではない。

## 2.2 工程仕様

### EX-01 リード(Lead)
| 項目 | 内容 |
|---|---|
| 入力 | 問い合わせ(CH1直接開拓・CH2発信・CH3紹介)・開拓リスト |

| 承認 | 一次応答=R(n8n定型)/不適格通知文=A/**無料相談の実施=H** |

### EX-02 事業監査(Business Audit)
| 項目 | 内容 |
|---|---|
| 入力 | A1受注(前払い入金確認)・事前資料・ヒアリング記録(人間実施) |
| 出力 | 監査報告書一式(報告書・現状分析・優先課題・戦略的方向・ロードマップ30/60/90日+1年) |

| 承認 | **ヒアリング実施=H/スコア確定=H/優先課題確定=H**。報告書の文面=A |
| 規律 | 監査は方向まで。解決策は語らない(W9)。内部14日工程を遵守 |

### EX-03 提案(Proposal)
| 項目 | 内容 |

| 承認 | 依頼文面=A(テンプレ承認後はR) |

## 2.3 工程間の共通規則

1. すべての工程は開始時にSTATEを読み、終了時にSTATEへ書く(Memory Agentのフックが強制)
2. 工程間の引き渡しはハンドオフ5行書式(FROM-TO/WHAT/BASIS/STATUS/NEXT)
3. どの工程でもRED_FLAG該当・支払遅延30日超はKill基準(HQ Core §1.9)の手続きへ
4. 顧客はどの段からでも降りられる。降りた顧客は終了ではなくN1育成へ(冷凍、廃棄しない)
5. 全工程の出口で収穫(H1)。1行でもよい——「今回速くできた理由/遅れた理由」を残す

## 4.3 案件→PBOS資産の変換規則(全案件に適用)

**規則1(全数収穫):** 完了・中止を問わず、クローズする全案件はEX-11を通過する。収穫ゼロのクローズをSTATE上で受理しない(Memory Agentが差し戻す)。

**規則2(資産3条件検査):** 収穫物は①次回を速く・安く・強くする ②属人でない形式(テンプレート・手順・部品・文例) ③GitHub `06_assets/` 格納——の3条件をLibrarianが検査。落ちたものは「メモ」としてSTATEに残し、資産とは呼ばない。

**規則3(収穫の標準5点):** 各案件で最低限、次の5種を点検する——(a)工数実績と差異の理由 (b)再利用できた部品と新たに作った部品 (c)顧客の言葉(価値が伝わった瞬間の表現) (d)検査で見つかった欠陥と追加検査項目 (e)次の同種案件への申し送り1行。

**規則4(失敗の等価性):** Failure LogはSuccess Logと同格の資産である。Kill案件の収穫を省略した場合、Kill手続き自体が未完了となる(HQ Core §1.9)。

**規則5(還流の締め):** 資産は格納で終わらない。四半期棚卸しで「再利用回数」を計測し、12ヶ月再利用ゼロの資産はアーカイブ候補(削除はしない)。再利用された資産の実績はEX-12の改善起案の根拠になる。
