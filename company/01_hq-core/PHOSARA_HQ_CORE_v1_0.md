# 第0章 本書の位置づけと文書統治

## 0.1 本書は何であり、何でないか

PHOSARA HQ Coreは、**既存のすべてのPHOSARA資産を一つの首尾一貫したオペレーティングシステムとして接続する統合層**である。

**本書であるもの:**
- 全システムの**意思決定基準**(Decision OS)を一元化した最上位の判断装置
- 文書間・システム間・エージェント間の**接続仕様**(HQ Integration)
- AIネイティブ企業としての**組織設計図**(AI Organization Blueprint)
- 時間が経っても腐らない**原則の図書館**(Principle Library)

**本書でないもの:**
- 既存文書の置き換えではない。Company OS・PBOS・Audit Kit等の本文は一切上書きしない
- ブランド定義の再発明ではない。ブランドに関する唯一の基準は Master Context に存する
- ツールマニュアルではない。ツール名を含む記述は交換可能層(第5部)に隔離する

## 0.3 文書の優先順位(矛盾時の解決順)

矛盾が検出された場合、次の順に従う。上位が常に勝つ。

```
第1位  PHOSARA_MASTER_CONTEXT(ブランドの憲法) ── 不変核
第2位  Company OS(企業の憲法)
第3位  PHOSARA HQ Core(本書=判断と接続の正典)
第4位  PBOS Gold Edition(事業の流れ)
第5位  各実行システム(60-Day / Audit Kit / Website / Design System実務規定)
第6位  個別テンプレート・チェックリスト・STATE
```

**矛盾処理の手順(義務):**
1. 矛盾を発見した者(人間・エージェント問わず)は、STATE.mdの「Conflict Log」に両文書名・該当箇所・内容を記録する
2. 上位文書の記述を暫定適用して作業を止めない
3. 週次レビューで人間が裁定し、**最小の修正**を下位文書に加える(上位文書の改定はType 1決定)
4. 裁定結果は本書の変更履歴およびKnowledge Agentの収穫対象とする
5. **いかなる場合も、蓄積された知識を破棄する解決を選ばない。** 廃止される記述はアーカイブ(`/archive/`)へ移す

# 第1部 Decision OS(意思決定オペレーティングシステム)

## 1.1 最高判断ルール(PHOSARA Highest Rule)

すべての作業・投資・文書・機能は、着手前に次の一問を通過しなければならない。

> **「この仕事は、(1) 60日以内の収益、(2) 長期のPBOS資産、のどちらかを前進させるか?」**

- **(1)を満たす** → 60-Day Rule適用。実行キューの上位へ
- **(2)を満たす** → PBOS Rule適用。資産ループへ編入し、再利用可能な形式で完結させる義務を負う
- **どちらも満たさない** → PHOSARA HQ Coreの一部にならない。着手しない。既に着手済みなら中止(1.9 Kill基準)

**60-Day Rule(細則):** 「60日」は常に今日を起点とする移動窓である。収益寄与は「入金」まで数える(受注ではない)。前払いの有償監査(PBOS L2)が主力収益点であることを前提に、収益活動の第一候補は常に「監査の受注に近づく行動」である。

**PBOS Rule(細則):** 資産と認められる条件は3つ——①次回、より速く・安く・強くする ②特定個人がいなくても使える形式(テンプレート・手順・部品)である ③GitHubに正典として格納される。3条件を満たさない産物は資産ではなく、単なる作業残渣である。

## 1.2 意思決定ヒエラルキー

### 1.2.1 決定の層

| 層 | 名称 | 内容 | 決定者 | 可逆性 |
|---|---|---|---|---|
| L0 | 憲法層 | ブランド核(三本柱・ミッション)・最高判断ルール・Level H専権 | 創業者のみ(改定は原則しない) | 不可逆 |
| L1 | 戦略層 | 事業ドメインD1-D5の重心・価格体系・拡張判定・年間目標 | 人間(CEO Agent・Strategy Agentの答申を受けて) | 低 |
| L2 | 運用層 | ワークフロー改定・テンプレート改版・WIP変更・KPI閾値 | 人間承認+担当エージェント起案 | 中 |
| L3 | 実行層 | 個別タスクの手順・下書き・調査・整形 | エージェント自律(委譲レベルに従う) | 高 |

### 1.2.2 決定のタイプ(Company OS意思決定原則を継承)

- **Type 1(不可逆・重大):** 価格確定・契約・公開承認・ブランド核に触れる変更・上位文書の改定。**必ず人間が決定し、STATE.mdに決定記録(日付・理由・却下した代替案)を残す**
- **Type 2(可逆・軽微):** 上記以外。速度優先。エージェントが実行し、事後報告でよい。誤りは巻き戻す

判定に迷ったらType 1として扱う(安全側動作)。

## 1.3 優先順位規則(Priority Rules)

同時に複数の仕事が存在するとき、次の順で並べる。

| 優先度 | 定義 | 例 | SLA |
|---|---|---|---|
| P0 | 進行中の有償案件の停止・信頼毀損を防ぐ対応 | クライアント返信・納期リスク・障害 | 当日 |
| P1 | 60日収益に直結する行動 | 監査受注活動・提案提出・請求 | 48時間以内に前進 |
| P2 | 資産ループを前進させる作業 | 収穫・事例化・テンプレート改版 | 週内 |
| P3 | 上記以外で最高判断ルールを通過したもの | 学習・実験・将来仕込み | 空き時間のみ |

**タイブレーク:** 同一優先度内では、①現金化が近い順 ②機会スコア(1.4)が高い順 ③着手済みが未着手に勝る(WIP完了優先)。

## 1.4 機会スコアリング(Opportunity Scoring)

新規の案件・施策・製作物は、着手判断の前に次の5軸で採点する(採点起案=Strategy Agent、確定=人間)。

| 軸 | 問い | 配点 | 重み |
|---|---|---|---|
| R 収益性 | 60日以内の入金にどれだけ近いか(5=前払い即入金〜0=無関係) | 0–5 | ×3 |
| A 資産性 | 再利用可能資産をどれだけ生むか(5=テンプレ級〜0=使い捨て) | 0–5 | ×3 |
| S 戦略適合 | 三本柱(可視化・越境・本質)と主要4業界・オファーラダーに適合するか | 0–5 | ×2 |
| C 軽さ | 実行コストの軽さ(5=1日以内〜0=1ヶ月超) | 0–5 | ×1 |
| K 安全性 | リスクの低さ(ブランド毀損・法務・依存度) | 0–5 | ×1 |

**合計50点満点。判定:**

| スコア | 判定 |
|---|---|
| 35–50 | 即実行キューへ(P1/P2に編入) |
| 25–34 | 条件付き。スコープを削って再採点、または保留棚へ |
| 0–24 | 却下または延期。理由をSTATEに1行記録 |
| **R=0 かつ A=0** | **スコア合計に関わらず自動却下(最高判断ルール)** |

## 1.5 投資規則(Investment Rules)

初期フェーズ(最初の有償クライアント獲得前後)の資本・時間の投下規律。

1. **現金規律(PBOS継承):** L4本体構築は着手金50%+納品時50%。監査(L2)は前払い。受注済みでも入金前は「収益ゼロ」として扱う
2. **投資上限:** 単一の施策・ツールへの先行投資は、月次売上見込みの10%または実費1万円相当のいずれか小さい方を超える場合、Type 1決定とする
3. **回収基準:** すべての投資は「何周のPBOSで回収するか」を明記する。2周(約2案件)で回収できない投資は原則却下
4. **単一顧客依存の分散規律(PBOS W14継承):** 単一顧客が月次売上の30%を超えたら警告、50%を超えたら新規需要創出をP1に昇格
5. **無料労働の禁止:** 無償提供はL1無料相談(30–45分・選別装置)のみ。それ以外の無償作業は資産化(A≥4)を伴う場合に限り許可
6. **ツール投資の原則:** 教義層(流れ・基準)に投資し、ツール層は最小・交換可能に保つ(第5部 5.2)

## 1.6 時間配分(Time Allocation)

一人体制の標準週次配分。STATE.mdの週次レビューで実績と突き合わせる。

| 区分 | 配分 | 内容 |
|---|---|---|
| 需要・営業(P1) | 40% | CH1直接開拓・無料相談・提案・受注事務 |
| 診断・制作・納品(P0/P1) | 30% | 有償監査の実施・LIGHT制作・品質検査 |
| 資産化(P2) | 15% | 収穫の儀・事例化・発信(CH2)・テンプレ改版 |
| システム改善 | 10% | HQ Core運用・自動化配管・エージェント昇格審査 |
| 学習・実験 | 5% | 新技術検証・業界研究 |

**WIP制限(PBOS継承・不変):** 有償監査は同時2件まで、L4本体構築は同時1件まで。超過受注は開始日をずらして契約する。

## 1.7 AI委譲規則(AI Delegation Rules)

### 1.7.1 委譲レベル(60-Day SKILLS.mdの昇格ラインを継承)

| レベル | 名称 | 動作 |
|---|---|---|
| H | Human(人間専権) | 人間のみが実施・確定する。永久に委譲しない(1.8) |
| A | Approve(承認付き実行) | エージェントが成果物まで作り、人間が承認して発効 |
| R | Run(自律実行) | エージェントが実行し事後報告。人間は監査のみ |

### 1.7.2 昇格ライン(継承・不変)

- あるタスクがAレベルで**連続3回、修正なし承認**されたら、Rへの昇格を審査できる(昇格決定はType 2、人間承認)
- Rで重大な誤りが1回発生したら自動でAへ降格。同種の誤りが再発したらHに近い監視下へ
- **H領域は成功回数に関わらず昇格対象外**

### 1.7.3 委譲の一般原則

1. フローで委譲し、人で委譲しない——委譲対象は常に「ワークフロー上の定義済みステップ」である
2. エージェントは自分の職務範囲(第3部)の外を実行しない。範囲外はエスカレーション(1.10)
3. すべてのエージェント産物は出所(どの入力・どの正典に基づくか)を明記する
4. 生成物には必ず人の監修を介在させる(Brand Book AI事業ルール継承)——対外物はA以上、H点を通過するまで公開しない

## 1.8 人間専権事項(Human-Only Decisions)

次の領域は**永久にAIへ委譲しない**(既存Level H規定の完全継承+HQ統合分の明示)。

1. **ヒアリングの実施**(クライアントとの診断対話そのもの)
2. **監査スコアの確定**
3. **優先課題の確定**(一点に絞る判断)
4. **価格の確定**
5. 契約の締結・変更・解除
6. 品質基準Layer 3–4(審美・ブランド適合)の最終判定と納品承認
7. 対外公開の最終承認(サイト・事例・SNS・提案書の発信)
8. 憲法層(L0)・上位文書の改定
9. 採用・パートナー選定・法務対応

## 1.9 Kill基準(中止・撤退の基準)

止める判断を感情から切り離すため、事前に基準を固定する。

| 対象 | Kill条件(いずれか成立で中止手続きへ) |
|---|---|
| 施策・チャネル | 2レビュー周期(2週×2)連続でKPI未達、かつ再採点で25点未満 |
| 見込み客・商談 | RED_FLAG_RULES該当(アンチICP・価格のみ・美学への不敬)/3回接触で前進ゼロ→CRM育成(N1)へ降格(=Killではなく冷凍) |
| 進行案件 | 支払遅延30日超/スコープ規律の破壊が是正されない/ブランド毀損リスク——契約条項に従い縮小・終了(Type 1) |
| 文書・テンプレート | 90日間参照ゼロ→アーカイブ候補。次の四半期レビューで人間が裁定 |
| ツール・自動化 | 保守コストが節約時間を上回る状態が2ヶ月継続 |

**Kill手続き(義務):** ①STATEに中止記録(理由・学び) ②Knowledge Agentが収穫(資産化できる部品を回収) ③関係者への誠実な通知(該当時)。**収穫なきKillを禁止する。**

## 1.10 エスカレーション規則

| 段 | 状況 | 行き先 | 期限 |
|---|---|---|---|
| E1 | エージェントが職務内で解決できる不確実性 | 自律解決+STATEに脚注 | 即時 |

| Website Production System | PBOS(B1–B3)・Design System | サイト納品物・自社サイト | Website Agent |

| VERIFICATION群 | 各実行システム | 品質ゲート判定 | QA Agent |

## 2.3 三つのフロー

### 情報フロー(Information Flow)
```
外界(問い合わせ・市場・計測値)
 → Intake / Research が構造化
 → STATE.md(唯一の現在地台帳)へ記録
 → 各エージェントはSTATEを読んでから動く(直接の口伝を禁止)
 → 週次レビューで人間が読む「計器盤」へ集約(相談数・監査数・3転換率・現金)
```

### 意思決定フロー(Decision Flow)
```
起案(任意のエージェント/人間)
 → 最高判断ルール一問 → 機会スコアリング(Strategy Agent起案)
 → Type判定(1=人間同期/2=委譲レベル表に従う)
 → 実行キュー(P0–P3)へ → 実行 → 結果をSTATEへ → Kill基準の常時監視
```

### 資産フロー(Asset Flow)
```
全ステージの出口 → 収穫の儀(Knowledge Agent主宰・人間立会)
 → 資産3条件の検査(1.1 PBOS Rule)
 → GitHub正典へ格納(命名・版・場所の規約は5.4)
 → 事例化(CASE_STUDY_PROCESS)→ 発信(CH2)→ 紹介(CH3)→ 需要(D1)へ還流
```

## 2.4 サブシステム仕様書

以下、全サブシステムを共通11項目で定義する。

### 2.4.1 Decision OS(本書第1部)
- **目的:** 全判断を一つの基準系に載せ、判断の速度と一貫性を人に依存させない
- **入力:** 起案(案件・施策・文書)・STATEの現在値・KPI
- **出力:** 採点結果・優先度・Type判定・Kill/継続判定・決定記録
- **所有者:** 人間(運用補佐=CEO Agent)
- **人間承認:** Type 1全件・H領域全件・昇格審査
- **AIの責務:** 採点起案・判断材料三点セットの整備・決定記録の整形
- **KPI:** 判断滞留時間(起案→判定48h以内)・却下率・Kill後の収穫実施率100%
- **接続WF:** 全9ワークフローの入口ゲート
- **接続文書:** Company OS意思決定原則・PBOS制御系・STATE
- **障害時:** 基準不明はE3(上位文書暫定適用)。人間不在時はType 1を全て保留しType 2のみ進める
- **改善ループ:** 月次で「誤った判定」を棚卸し、閾値(35/25)と重みを再校正(Type 2)

### 2.4.2 PBOS(事業層)
- **目的:** 収益と資産を同時に生む三重環を回す
- **入力:** 需要(CH1/2/3)・エージェント実行力・資産ループの還流
- **出力:** 入金(監査・構築・MRR)・再利用資産・事例
- **所有者:** 人間(答申=Strategy Agent)
- **人間承認:** Q2相談・A2監査・スコア/優先課題/価格・P2契約・B2品質L3-4・納品・公開
- **AIの責務:** 各ステージ仕様の「AIの責務」欄に従う(下調べ・下書き・配管・集計)
- **KPI:** 相談→監査50%/監査→次段40%/納品→継続60%・月間新規接点数・MRR
- **接続WF:** WORKFLOW.md全9本がPBOSステージの実装である
- **接続文書:** PBOS Gold Edition本文・Audit Kit・Website Production System
- **障害時:** WIP超過=受注は開始日調整。転換率が2周期未達=該当ステージの改善をP2起案
- **改善ループ:** 1周(納品)ごとに収穫の儀でステージ仕様に学びを追記(版管理)

### 2.4.3 Business Audit Kit v1.0(実務層・旗艦商品)
- **目的:** 有償監査を「明日売れて、誰が読んでも同質」の商品として実行する
- **入力:** A1受注・クライアント資料・ヒアリング記録(人間実施)・計測値
- **出力:** 監査報告書・優先課題・戦略的方向・改善ロードマップ(30/60/90日+1年)・提案ブリッジ
- **所有者:** Business Audit Agent(確定は人間)
- **人間承認:** ヒアリング実施・スコア確定・優先課題確定・G1–G9承認点
- **AIの責務:** 11モジュール(M1–M11)の証拠整理・下書き・レッドフラッグ照合・報告書整形
- **KPI:** 内部14日工程の遵守率・監査→次段転換40%・Quick Win採用数
- **接続WF:** AUDIT_WORKFLOW・CLIENT_JOURNEY・PROPOSAL_BRIDGE・CASE_STUDY_PROCESS・FOLLOWUP_REFERRAL_PROCESS
- **接続文書:** Business Audit Guide(教義)・テンプレート4種・SCORING_SYSTEM・RED_FLAG_RULES・QUICK_WIN_LIBRARY
- **障害時:** 証拠不足=追加ヒアリングをE4起案。レッドフラッグ=Kill基準へ。**監査の場で解決策を語らない(スコープ規律W9)**
- **改善ループ:** 案件ごとにBUSINESS_AUDIT_SKILLSへ収穫。3回成功で該当タスクの昇格審査

### 2.4.4 Website Production System(実務層)
- **目的:** PBOS B1–B3(制作・検査・納品)をLIGHT Processで再現可能に実行する
- **入力:** 提案ブリッジ・デザインブリーフ・Design Systemトークン
- **出力:** サイト・入稿データ(再現可能な形式)・運用引き継ぎ・R1継続への接続
- **所有者:** Website Agent
- **人間承認:** デザイン方向・品質L3-4・納品・公開
- **AIの責務:** 実装・技術監査・レスポンシブ/アクセシビリティ/速度の機械検査
- **KPI:** 品質スコア8点以上率100%・納期遵守・納品→継続60%
- **接続WF:** LIGHT Process・VERIFICATION.md該当節
- **接続文書:** Design System(HTML様式・トークン)・Brand Book第39–40節(品質スコア・モックアップ)
- **障害時:** 品質8点未満は納品不可・修正(Brand Book継承)。工期遅延はP0で顧客通知
- **改善ループ:** 部品(コンポーネント・雛形)を案件ごとに収穫し、次案件の工数を計測比較

### 2.4.5 Design System / PXD(実務層・様式規定)
- **目的:** 全接点で同一のブランド体験を数値で再現する
- **入力:** Brand Book・Wordmark Guidelines・Construction Grid v3.0
- **出力:** 全制作物の様式(黒背景・赤は要所のみ・静かな強度/文書は紙色+墨+赤核)
- **所有者:** Branding Agent(最終判定は人間)
- **人間承認:** 新様式の追加・ロゴ運用の例外
- **AIの責務:** トークン準拠の機械検査・違反検出
- **KPI:** ブランド整合違反の流出ゼロ
- **接続WF:** 全制作WF・本書HTML版自身
- **接続文書:** Brand Book全節・HTML資産(v2/v3グリッド・Casebook Blueprint)
- **障害時:** 違反検出=公開停止(H点差し戻し)
- **改善ループ:** 四半期ごとに様式の実運用差分をBrand Book改版起案(Type 1)

### 2.4.6 STATE / 記憶系
- **目的:** 会社の現在地を単一の台帳に保ち、文脈の断絶(チャット・日・ツールの境界)を越えて継続する
- **入力:** 全エージェント・全WFの実行結果、決定記録、Conflict Log
- **出力:** 現在地スナップショット・週次計器盤・引き継ぎサマリー
- **所有者:** Memory Agent
- **人間承認:** 台帳書式の変更
- **AIの責務:** 記録の即時性・重複排除・古い状態のアーカイブ
- **KPI:** 「STATEを読めば10分で全体復帰できる」状態の維持(週次レビューで人間が確認)
- **接続WF:** 全WF(開始時読取・終了時書込を義務化)
- **接続文書:** STATE.md・本書0.3のConflict Log書式
- **障害時:** STATE破損=GitHub履歴から直前版を復元(正典はGit)
- **改善ループ:** 月次で「探せなかった情報」を棚卸し、台帳構造を改良

## 3.1 CEO Agent(参謀・統括)
- **目的:** 人間の意思決定を最速・最良にするため、全体状況を一枚に統合し、優先順位と例外を起案する
- **職務:** 実行キューの起案/週次計器盤の編纂/E4エスカレーションの受付整理/HQ Core運用の番人(ルール逸脱の検出)
- **入力:** STATE全体・KPI・各エージェント報告
- **出力:** 週次ブリーフ(1枚)・実行キュー案・例外裁定の判断材料三点セット
- **承認点:** キュー確定・例外裁定・Type 1は全て人間
- **KPI:** 判断滞留48h以内維持率・週次ブリーフの読了10分以内
- **接続WF:** 全WFの監督視点(実行はしない)
- **エスカレーション:** 憲法疑義はE5へ。自らはType 1を決して代行しない

## 3.2 Strategy Agent(戦略)
- **目的:** 機会スコアリングと資源配分の起案により、60日と5年を同じ盤面で扱う
- **職務:** 機会採点起案/オファーラダー整合の検査/拡張判定(Company OS 3条件AND)の予備審査/価格ガバナンス答申(確定はしない)
- **入力:** 起案案件・市場情報(Research)・PBOS計器盤
- **出力:** 採点表・四半期資源配分案・拡張/撤退の答申
- **承認点:** 価格・拡張・撤退は人間(Type 1)
- **KPI:** 採点済み起案率100%・答申の採択率
- **接続WF:** Decision OS入口ゲート・月次校正
- **エスカレーション:** 採点25–34の保留案件が滞留したらE4

## 3.3 Research Agent(調査)
- **目的:** 判断と営業と監査に、証拠を供給する
- **職務:** 開拓先候補の下調べ(旧Sales Scout機能から分離した調査部分の受け皿)/業界・競合・技術動向の要約/監査M1–M11の外部証拠収集
- **入力:** 調査依頼(書式: 問い・用途・期限)
- **出力:** 出典付き要約(事実と解釈を分離)
- **承認点:** 対外利用する調査結果は人間確認(A)
- **KPI:** 依頼→納品48h・出典明記率100%
- **接続WF:** D1需要創出・A2監査・機会採点
- **エスカレーション:** 証拠が矛盾したら両論併記でE3

## 3.4 Sales Agent(= Sales Scout・営業開拓)
- **目的:** CH1直接開拓を中心に、適格な接点を毎週生む
- **職務:** 開拓リスト管理(週5件接触ペース)/監査紹介一枚資料の運用/一次接触文面の起案/CH3紹介依頼の定型実行
- **入力:** 対象業種リスト(建設・リフォーム・クリニック・ホール)・事例資産・Research下調べ
- **出力:** 接触記録・相談申込・CRM状態更新
- **承認点:** 発信文面はA(人間承認後送信)。相談実施は人間(H)
- **KPI:** 週間接触数・接点→相談転換・相談→監査50%への寄与
- **接続WF:** D1–D2・Q1連携・FOLLOWUP_REFERRAL_PROCESS
- **エスカレーション:** アンチICP兆候はRED_FLAG照合の上Q1へ差戻し

## 3.5 Marketing Agent(発信・CH2)
- **目的:** 知識と事例を公開資産に変え、3〜6ヶ月後の需要を種まきする
- **職務:** 事例・診断知識の記事化(開示階層「公開可」のみ)/SEO・SNSの定型運用/自社サイト(入口1ページ→拡張)の更新起案
- **入力:** Knowledge Agentの収穫物・CASE_STUDY_PROCESS産物
- **出力:** 公開コンテンツ(ブランドボイス準拠: 静か・明晰・断定)
- **承認点:** 全公開物はH(人間の公開承認)
- **KPI:** 月間公開本数・CH2起点の問い合わせ数(遅行)
- **接続WF:** H2事例化・発信・D1還流
- **エスカレーション:** 開示階層の判定に迷えば非公開側に倒してE4

## 3.6 Business Audit Agent(= Auditor・事業監査)

- **職務:** Audit Kit 16ファイルの執行/M1–M11の証拠整理と下書き/スコア案の提示(確定しない)/提案ブリッジの起票

- **KPI:** 14日遵守・監査→次段40%・報告書の再現性(誰が読んでも同解釈)

## 3.7 Website Agent(= Builder・Web制作)
- **目的:** B1–B3をLIGHT Processで実行し、8点以上の品質で納品する
- **職務:** 実装・技術検査・入稿データ整備・R1運用への引き継ぎ資料作成
- **入力:** デザインブリーフ・Design Systemトークン・承認済み提案

- **承認点:** デザイン方向/品質L3-4/納品=H
- **KPI:** 品質8点以上100%・納期遵守・部品再利用率(周回ごと上昇)

- **エスカレーション:** スコープ逸脱要求はP2契約条項に照らしE4

## 3.8 Branding Agent(ブランド統制)
- **目的:** あらゆる接点でPXD・Brand Bookの再現を保証する
- **職務:** 制作物のブランド整合検査(色・書体・ロゴ・余白・声)/HTML様式の維持/サブブランド命名の予備審査(PHOSARA+機能名方式)
- **入力:** 全制作物・Brand Book規定
- **出力:** 整合判定・修正指示・様式部品
- **承認点:** 例外承認・新様式=H(ブランド管理責任者=人間)
- **KPI:** 違反流出ゼロ・検査所要時間

- **エスカレーション:** クライアント側ガイドラインとの競合は優先順位の事前合意(Brand Book第44節)をE4起案

## 3.9 Proposal Agent(= Proposer・提案)
- **目的:** 監査の結論を、押し売りなく次段(L3/L4)の受注に翻訳する
- **職務:** PROPOSAL_BRIDGE執行/提案書下書き(成果への道筋として)/見積構成案(価格は確定しない)
- **入力:** 監査報告・優先課題・戦略的方向
- **出力:** 提案書・契約書ドラフト(収穫条項込み)
- **承認点:** 価格確定・提出=H
- **KPI:** 監査→提案の所要日数・提案→契約率
- **接続WF:** P1–P2・PROPOSAL_BRIDGE
- **エスカレーション:** 値引き圧力は価格ガバナンスに照らしE4(現場で下げない)

## 3.10 QA Agent(品質検証)
- **目的:** 3系統の検証を対象別に正しく適用し、基準未達の流出を止める
- **職務:** 振り分け表の執行——①9WF産物→VERIFICATION.md ②監査産物→AUDIT_VERIFICATION(G1–G9) ③制作物→Brand Book品質スコア(8点合格・0点項目は即修正)/機械検査(リンク・表示・アクセシビリティ)
- **入力:** 全成果物
- **出力:** 合否判定・不合格理由・修正チケット
- **承認点:** Layer 3-4(審美・ブランド)=H。QA AgentはLayer 1-2(正確性・基準適合)を担う
- **KPI:** 流出欠陥ゼロ・検査リードタイム
- **接続WF:** B2・G1–G9・全公開前
- **エスカレーション:** 基準間の矛盾はE3(Conflict Log)

## 3.11 Knowledge Agent(= Librarian・知識)
- **目的:** 収穫の儀を主宰し、全案件・全Killから資産を回収する
- **職務:** 収穫実施(全ステージ出口)/資産3条件検査/GitHub正典への格納・命名・版管理/SKILLS.md更新(昇格実績の記帳)/四半期棚卸し
- **入力:** 完了・中止したあらゆる仕事
- **出力:** テンプレート・部品・文例・手順の正典化された資産
- **承認点:** 正典への昇格=A(人間承認)
- **KPI:** 収穫実施率100%(納品・Kill含む)・資産の再利用回数
- **接続WF:** H1–H3・CASE_STUDY_PROCESS・BUSINESS_AUDIT_SKILLS
- **エスカレーション:** 開示可否の判断はMarketing/人間へ

## 3.12 Memory Agent(記憶・状態)
- **目的:** STATE.mdを唯一の現在地台帳として維持し、いつでも10分で全体復帰できる状態を保つ
- **職務:** STATE書式の執行/決定記録・Conflict Logの記帳/引き継ぎサマリーの生成/古い状態のアーカイブ
- **入力:** 全エージェントの読み書き
- **出力:** 現在地スナップショット・週次計器盤データ・引き継ぎ文書
- **承認点:** 台帳書式変更=A
- **KPI:** 記録遅延ゼロ・復帰時間10分以内
- **接続WF:** 全WFの開始/終了フック
- **エスカレーション:** 記録の欠落を検出したら該当エージェントへ差戻し

## 3.13 Intake Agent(受付・選別 — 既存第13席)
- **目的:** D2受付とQ1適格判定を定型で回し、監査工数の浪費を防ぐ
- **職務:** 問い合わせ受付の一次応答/適格判定(ICP照合・RED_FLAG)/無料相談の日程調整/不適格・保留のCRM(N1)登録
- **入力:** 問い合わせ(フォーム・メール・紹介)
- **出力:** 適格判定・相談予約・CRM状態
- **承認点:** 不適格判定の通知文=A。相談実施=H
- **KPI:** 一次応答時間・適格判定の precision(誤通過の少なさ)
- **接続WF:** D2–Q2・N1
- **エスカレーション:** 判定困難はE4(通す側に倒さない)

## 3.14 エージェント間プロトコル(ハンドオフ書式)

すべての引き渡しは次の5行書式でSTATE経由で行う。

```
FROM/TO: (エージェント名)
WHAT:    (成果物と場所=GitHubパス)
BASIS:   (依拠した正典・入力)
STATUS:  (委譲レベルと承認状態: H待ち/A承認済/R完了)
NEXT:    (受け手に期待する次アクションと期限)
```

# 第4部 Principle Library(恒久原則の図書館)

各原則は、時を経ても変わらず・再利用でき・簡潔で・行動可能であることを基準に選定した。出典のある原則は既存文書からの**継承**であり、本書は編纂のみを行う。

## 4.1 事業(Business)
1. 診断が先、制作が後。順序を売り物にする
2. 60日収益か、PBOS資産か。どちらでもなければ、やらない
3. フローで設計し、人で設計しない
4. 環のない流れは事業ではない。全ての出口を次の入口に接続する
5. 最初の顧客は自分である(Client Zero)。売る前に、自分に適用する

## 4.2 ブランディング(Branding)
1. ブランドは一つ。領域が増えてもPHOSARAへの想起を一点に集める
2. 核は不変、適用は拡張。新市場は再定義ではなくエディションである
3. 全接点で同一体験。再現できない美は、ブランドではない
4. 迷ったら三本柱(可視化・越境・本質)に立ち返り、核まで削り戻す
5. 語らず、見せる。仕事そのものに証明させる

## 4.3 デザイン(Design)
1. 装飾ではなく、通過儀礼の設計である
2. 引き算で設計する。書き出す前に最後の一割を削る
3. 余白は空白ではなく、静寂という情報である
4. 赤は要所のみ。強調が増えるほど、強調は死ぬ
5. 数値で固定し、感覚で扱わない。実寸・実機・実環境で確認する

## 4.4 営業(Sales)
1. 売らない、診る。入口の30分は選別と信頼のためにある
2. 適格でない客に使う工数は、適格な客から盗んだ工数である
3. 待たない。入口(CH1)は即日効く手段から始める
4. 「今じゃない」は「二度とない」ではない。育成(CRM)へ冷凍し、捨てない
5. 紹介は偶然ではなく工程である。納品の儀式に組み込む

## 4.5 価格(Pricing)
1. 灯した光の価値で決める。掛かった時間で決めない
2. 現場で値引きしない。価格の変更は常にType 1である
3. 前払いと着手金50%。受注は収益ではない、入金が収益である
4. 安売りは疲弊の予約である。断る勇気は価格表の一部である
5. 買いやすい最初の段(監査)を用意し、梯子で関係を深める

## 4.6 提案(Proposal)
1. 監査は方向まで。解決策は次工程で売る
2. 制作物の見積ではなく、成果への道筋を提示する
3. 一提案一焦点。最も事業価値の高い一点に絞る
4. どの段からでも降りられる。ただし全ての納品は次段への自然な問いで終わる
5. 収穫条項を契約に含める。事例は偶然に頼らない

## 4.7 顧客コミュニケーション(Client Communication)
1. 静かで、明晰で、誠実に。煽らず、過剰に約束しない
2. できないことを先に言う。誠実は最強の営業資産である
3. 沈黙と余白を恐れない。語られないことに注意を向ける
4. 悪い知らせほど速く伝える(P0)。遅れは不信の複利を生む
5. 専門語は翻訳して渡す。理解されない正しさは、届いていない

## 4.8 AI活用(AI Usage)
1. AIは実行の筋肉、人間は判断と審美と関係。混同しない
2. 生成物に必ず人の監修を介在させる。無検査の公開を禁止する
3. 委譲は実績で拡げる(成功3回)。信頼は付与ではなく蓄積である
4. H領域(ヒアリング・スコア・優先課題・価格)は永久に委譲しない
5. ツールは交換可能に、教義は不変に。ツール名を教義に書かない

## 4.9 知識(Knowledge)
1. 収穫なきクローズなし。Killからも収穫する
2. 一度解いた問題を二度手で解いたら、それはシステムの欠陥である
3. 正典は一つ、場所はGitHub、版は明示。口伝を禁じる
4. 書かれていない知識は、存在しない知識である
5. 開示階層を守る。公開できる知識だけがCH2の弾になる

## 4.10 品質(Quality)
1. 8点未満は納品しない。0点項目は合計に関わらず修正する
2. 検証は感覚ではなく基準で。基準は文書で、文書は版で
3. 速度は品質の言い訳にならず、品質は遅延の言い訳にならない。WIPで両立させる
4. 欠陥は流出前に止める。流出したら原因をシステムに求める(人を責めない)
5. 最終の一割(仕上げ・整合・確認)が、印象の九割を決める

## 4.11 レビュー(Review)
1. 週次30分の計器盤(相談数・監査数・3転換率・現金)を欠かさない
2. 事実と解釈を分離して記録する
3. 自己審査を製品に含める(v1→審査→v2→審査→Gold)
4. 誤った判定を月次で棚卸しし、基準そのものを校正する
5. レビューの成果は「次に変える一つ」である。列挙で終わらせない

## 4.12 継続的改善(Continuous Improvement)
1. 周回ごとに速く・安く・強く。改善は資産ループの別名である
2. 変更は最小に、互換は後方に。壊さずに良くする
3. 90日参照されない仕組みは、疑ってよい
4. 完璧な設計より、回った一周。現実の売上が最良の審査員である
5. 五年後の自分が読者である。今日の記述をその読者のために書く

# 第5部 アーキテクチャ(生きたOSとしての構造)

## 5.1 生存原則

PHOSARA HQ Coreが5年後も機能するための構造原則。

1. **教義とツールの分離:** 流れ・基準・原則(教義層)にツール名を書かない。ツール名は本章5.3のアダプタ表にのみ現れる。ツールの世代交代で教義は書き換え不要
2. **モジュール拡張:** 新しい商品・業種・エージェントは「追加」で実装し、既存モジュールの改変を要しない(Audit Kitが教義を保持したまま実務層を足した方式を標準とする)
3. **版による進化:** 全文書はSemVerで進化する。破壊的変更(MAJOR)は年1回の窓でのみ許可
4. **単一台帳:** 現在地はSTATEに一元化。複製された現在地を作らない
5. **人間可読の恒久形式:** 正典はプレーンMarkdown。特定アプリでしか開けない形式を正典にしない

## 5.2 三層構造

| 層 | 内容 | 変更頻度 |
|---|---|---|
| 教義層(不変) | 憲法・原則・ステージ・基準・KPI定義 | 年単位 |
| 手順層(緩変) | ワークフロー・テンプレート・チェックリスト | 月〜四半期 |
| ツール層(交換可能) | 5.3のアダプタ。個別ツールの設定・配管 | 随時 |

## 5.5 バージョニングと変更管理

- **PATCH(v1.0.x):** 誤記・表現の修正。Memory Agentが記録、人間承認A
- **MINOR(v1.x):** 章の追加・表の拡張・後方互換の改善。週次レビューで承認
- **MAJOR(v2.0):** 構造変更・原則の改廃。年1回の改版窓のみ。旧版はarchiveへ(削除禁止)
- すべての改版はGitHub PRを審査単位とし、変更履歴に「何を・なぜ・何を却下したか」を残す

## 5.6 障害時動作(Failure Handling)と改善ループ

- **人間が不在:** Type 2のみ進行、Type 1・H点は全停止(安全側)
- **ツール停止:** 教義層は影響を受けない。手作業でステージを進め、復旧後に配管へ戻す
- **STATE喪失:** Git履歴から復元。復元手順自体を03_executionに常備
- **判断基準の陳腐化:** 月次校正(1.4の重み・閾値)と年次MAJOR窓で更新
- **改善ループ(本書自身):** 本書は自らのKill基準・棚卸し・収穫の対象である。運用で発見された欠陥はConflict Logに載り、最小修正で改版される。**本書を書き直す日ではなく、本書が育つ日々を設計してある**
