# SCORING_SYSTEM.md — 採点・信号・レーダー・優先順位の規則

**教義(不変):** スコアは「価値がどの程度、可視化・一貫・再現されているか」の尺度。**優劣の評価ではなく、改善優先度の可視化。** 低スコア=劣っているではない。

---

## 1. 5段階スコア(既存教義を全モジュールに適用)

| スコア | 状態 | 改善優先度 |
|---|---|---|
| 1 | 可視化されていない | 最優先 |
| 2 | 部分的に可視化されている | 高 |
| 3 | 一定程度可視化されている | 中 |
| 4 | 概ね可視化されている | 低 |
| 5 | 十分に可視化され、再現可能 | 現状維持 |

**採点の規律:** ①チェックリストの記号分布から機械的に出さない(❌の数ではなく構造で判断)②迷ったら低い方(改善余地を見逃すより安全)③スコアの根拠となる代表エビデンスを1つ必ず紐付ける ④5は安易に出さない(5=「同業に見せて手本になる水準」)。

## 2. 信号評価(Traffic Light)— 顧客向けの直感表示

| 信号 | スコア | 意味(顧客向け文言) |
|---|---|---|
| 🔴 赤 | 1-2 | 価値が失われている(機会損失が現に発生) |
| 🟡 黄 | 3 | 機能しているが、伸びしろが明確 |
| 🟢 緑 | 4-5 | 強み(ここは守り、活かす) |

**使い分け:** 数字(スコア)は分析の言葉、信号は経営者の言葉。報告書では両方を併記する。**緑を必ず提示する**——診断は欠点探しではなく、強みの確認でもある(信頼の土台)。

## 3. 二枚のレーダーチャート

### レーダーA: 6領域(戦略の一枚)
Value / Market / Customer / Brand / Communication / Organization の6軸。**報告の主役。** 経営構造のどこが痩せているかを一目で示す。

### レーダーB: 11モジュール(実務の一枚)
M1〜M11の11軸。網羅性の証明と、具体的な着手点の議論用。

### 集約規則(モジュール→領域)
各領域のスコア = 対応モジュール群のスコアを参考に、**人間が総合判定**(機械平均しない。例: Communication配下の7モジュールで、事業影響の大きいものに重みを置く)。判定理由を一行残す。

### デザイン規定(PXD準拠)
- 背景: 黒(#0A0A0A)/ グリッド線: 暗灰 / スコア線: **一本の赤(ブランドの核色)** / 文字: 白・静かなサンセリフ
- 装飾なし。数字は小さく、形で語らせる。2枚は同一スケール(1-5)で並置
- 生成はSVG(skill: radar-chart-gen)。報告書PDF・プレゼン共用

## 4. 優先順位づけ(診断の結論を作る)

### 手順
1. 🔴と🟡の発見をすべて列挙(漏出点リスト)
2. 各項目を2軸で仮評価: **事業価値への影響度(大/中/小)× 着手の性質(自力で可能/専門支援が必要)**
3. **影響度・大**から上位3点を選ぶ(着手の容易さで選ばない——教義)
4. 3点のうち、他の課題の根にある**構造的要因**を1点特定 → **最優先課題**
5. 残りの「自力で可能×即効」の項目 → **クイックウィン**へ回す(ロードマップの30日枠)

### 判定の型(症状と構造の切り分け)
「問い合わせが少ない(症状)」の根が「サイトが古い(症状)」のさらに根の「強みが言語化されていない(構造)」にある——という掘り下げを必ず1段行う。**最優先課題は可能な限り構造側から選ぶ。** 構造を直せば症状群がまとめて動くからであり、これが「一点に絞る」教義の実務的根拠である。

## 5. スコア較正(ブレを防ぐ)

- 初回3案件は、採点後に「もし同業の手本企業なら何点か」を各領域で自問し、天井の感覚を較正する
- 案件ごとにスコア分布をlogs/へ記録し、自分の採点癖(甘い/辛い領域)を四半期で振り返る
- AIのスコア案と人間の確定値の差分も記録する(差分パターンはAI較正の学習データ=収穫)
