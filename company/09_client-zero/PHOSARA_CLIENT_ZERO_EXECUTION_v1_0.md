# 第0章 位置づけと特殊条件の裁定

Client Zeroは「PHOSARAがPHOSARAを監査する」案件である。既存工程を変えずに実行するため、自己案件に固有の3条件を先に裁定する(いずれも既存規範の適用であり、新規則ではない):

| # | 特殊条件 | 裁定 |
|---|---|---|
| Z-1 | クライアント=創業者自身(ヒアリングの両側が同一人物) | ヒアリング実施=H(人間)は不変。運用は「自己ヒアリング・プロトコル」(§5.4)により、AIが質問体系を逐語で進行し、人間が書面で即答する。回答の事後修正を禁止し原文を保存する |
| Z-2 | 自社サイトが未公開(監査対象の不在) | **不在そのものが監査所見である。** Website監査は「入口の不在による価値漏出」を証拠付きで記述し、要件を導出する。最小入口1ページの制作は監査の処方として優先課題分析(CZ-06)以降で扱う——監査より先に作らない(診断が先の憲法) |
| Z-3 | 無償案件(入金がない) | 入金主義により収益ゼロと記録する。ただしA1開始条件「入金確認」は「見本請求書の発行+入金記録の模擬記帳」に読み替え、配管AP-02のテストとする。60日ゴールの「有償監査2件」にClient Zeroは**算入しない** |

# 第3部 実行ワークフロー(CZ-01〜CZ-13)

### CZ-02 内部キックオフ(Internal Kickoff)【Day 1】
- 目的: 範囲と規律の宣言——「監査は方向まで。制作の話をしない」を自分に課す

- 検証: 除外事項の明記(スコープ規律)【G2相当】

### CZ-03 事業監査(Business Audit)【Day 2–5/EX-02】

### CZ-04 ウェブサイト監査(Website Audit)【Day 6–7】
- 目的: 入口の現状(不在を含む)を診断し、価値漏出を定量・定性で記述する

### CZ-05 ブランド監査(Brand Audit)【Day 8–9】

# 第5部 品質基準(Quality Standards)

## 5.1 受入基準

各成果物はG1–G9(監査系)+品質スコア(体裁物: 8点合格・0点即修正)+**「実クライアントにそのまま出せるか」テスト**(自社向けの手抜き体裁を禁止する)に合格すること。

## 5.2 レビュー・チェックリスト(CZ-09で使用)

- [ ] 全スコアに証拠が紐づく(証拠なきスコア=不合格)
- [ ] 優先課題は一点か。影響度基準か
- [ ] 監査は「方向まで」に留まっているか(解決策の詳細設計が混入していないか)
- [ ] 提案の価格はPricing Governanceの表内か
- [ ] ロードマップは60日計画と単一か
- [ ] 事例の開示区分は正しいか(内部原価・未確定戦略は非公開)
- [ ] ブランドボイス(静か・明晰・断定)・様式(Brand Book)準拠か
- [ ] 工数実測が全工程で記録されているか

## 5.3 不合格条件と手戻り規則

| 不合格条件 | 手戻り |
|---|---|
| 証拠なきスコアの発見 | 該当モジュールをDay 2–9の該当工程へ差し戻し(最大2日) |
| 優先課題が複数のまま | CZ-06をやり直す(統合をやり直すのであり、監査はやり直さない) |
| 品質スコア8点未満/0点項目 | 該当成果物のみ修正・再検査(全体を止めない) |
| 工程が計画比+7稼働日超過×2回 | 一旦クローズ判定へ: 完了済み監査分だけで縮小完了とし、残りをP2タスク化(Kill基準の精神——ただし収穫は必ず実施) |
| 自己欺瞞の兆候(§5.4違反) | 該当回答を破棄し、外部視点(第三者インタビュー)を必須化して再実施 |

## 5.4 自己ヒアリング・プロトコル(自己欺瞞対策)

1. AIが質問体系(テンプレートの設問)を**逐語で・順番どおり**進行し、飛ばし・先回りをしない
2. 人間は書面で即答し、**回答の事後編集を禁止**(原文をそのまま保存。訂正は追記形式)
3. 回答と証拠を分離する——「そう思う」はスコアの根拠にならない。三証拠源(資料・観察・計測)で裏を取れない回答は「未証明」とラベルする
4. スコアのタイブレークは**厳しい側に倒す**(自社案件の恒久規則)
5. 48時間の冷却: スコア案の作成(Day 5/7/9)と確定(H)の間に最低一晩置く
6. 可能なら第三者1名の外部視点(§2.2)を証拠に加える

| 3. 営業資料 | 監査紹介一枚資料に「自社適用済み」の節を追加(CH1直接開拓で使用)。誠実の証明として機能させる | Sales Scout |

| 5. 監査の実例(教材) | Audit Kitの各モジュールに「Client Zero記入例」として参照リンクを付す(Kit本文は無改変・リンク追加のみ) | Auditor+Librarian |

## 7.2 どう記録し、どこに置くか

各工程の出口で1行以上をSTATEへ(即時)。CZ-12でLibrarianが資産3条件を検査し、合格分をGitHub `06_assets/` へ正典化、不合格分はメモとしてSTATEに残す。SKILLS.mdには全エージェントの本件実績(A承認の成否)を記帳し、昇格カウントを開始する。

## 7.3 PBOSはどう更新されるか

CZ-13で「次に変える一つ」を確定→該当ステージ仕様/工程/テンプレへの**最小差分PR**→週次レビューで承認(手順層=A/教義層=Type 1)。更新は必ず実測(工数・欠陥・引っかかり)を根拠とし、感想を根拠にしない。

## 7.4 将来の監査はどう良くなるか

2件目(初の有償監査)は、①ベースライン工数との比較で見積精度が上がり ②記入例により下書き速度が上がり ③追加された検査項目により欠陥が減る。**この3点の実測比較そのものを2件目の収穫項目に予約する**(改善が起きたことを証明する仕組み)。
