# PHOSARA 60-Day Revenue Agent System v1.0

**目的:** 60日以内に最初の有償クライアントを獲得しながら、再利用可能なPBOS資産を蓄積する「自己改善型オペレーティングシステム」を、Claude Code上で稼働させる。
**上位文書:** PBOS Gold Edition(事業フロー)/ Company OS v1.0(権限・品質・自律度)
**本書の役割:** 6ファイル構成のシステム全体の説明書(マスタードキュメント)

---

## 0. 最終判断ルール(Ultimate Decision Rule)

すべてのタスクは、実行前に次の2条件のいずれかを満たすことを確認する。

> **条件1:** 60日以内の初回有償クライアント獲得の確率を直接高めるか?
> **条件2:** PHOSARAを恒久的に改善する再利用可能なPBOS資産を生むか?

**どちらも満たさないタスクは延期する。** このルールは他のすべての最適化判断に優先する。全エージェントのシステムコンテキストの冒頭に本ルールを配置し、人間も毎朝これで当日タスクを選別する。

---

## 1. システム構成(6ファイルの関係)

```
PHOSARA_60DAY_REVENUE_AGENT.md ← 本書(全体像・起動方法・60日計画)
├── STATE.md        … 現在地(KPI計器盤・パイプライン・WIP)。毎日更新される唯一の「今」
├── AGENTS.md       … 働き手(サブエージェント定義・権限・禁止事項・承認点)
├── WORKFLOW.md     … 仕事の手順(8ワークフロー。Explore→…→Improveの共通ループ)
├── SKILLS.md       … 蓄積(成功したワークフローをスキルへ昇格させる仕組み)
└── VERIFICATION.md … 検証(チェックリスト・ログ形式・週次レビュー・Hooks)
```

**読み順:** 人間は本書→STATE.md(毎日)。Claude Codeのエージェントは、起動時に必ず STATE.md → 該当ワークフロー(WORKFLOW.md)→ 関連スキル(skills/)の順で文脈を読み込む。

## 3. 共通動作ループ(全ワークフローの背骨)

```
Explore(探索: STATE.md・過去ログ・関連スキルを読む)
→ Plan(計画: 最終判断ルールで適格確認 → 手順とゴールを1画面に)
→ Implement(実装: エージェントが実行。承認点では必ず停止)
→ Verify(検証: VERIFICATION.mdのチェックリスト通過)
→ Report(報告: STATE.md更新+人間へ要約)
→ Learn(学習: 成功/失敗をlogs/へ記録)
→ Improve(改善: 3回成功したらスキル昇格、失敗したら手順改訂を提案)
```

**鉄則:** Reportを省略した作業は「なかったこと」になる(STATE.mdが更新されない=会社が現在地を見失う)。Learnを省略した作業は「複利にならない」。この2工程はいかなる場合も省略禁止。

## 4. 人間の承認点(Level H)一覧

Company OS 7.2に基づき、以下は**必ず人間の承認を経る**。エージェントは該当地点で停止し、承認依頼を出す。

1. 開拓メッセージ・営業メールの**送信**(下書きはAI、送信ボタンは人間)
2. 価格の提示(監査価格・提案見積)
3. 監査スコアと優先課題の確定
4. 提案書の提出
5. 契約の締結
6. 制作物の中間レビュー(コンセプト整合)と納品
7. 事例・記事など**あらゆる公開**
8. リードの辞退・育成行きの判定

## 5. 60日フェーズ計画

| フェーズ | 日 | 主目標 | 主ワークフロー |
|---|---|---|---|
| Phase A: 装填 | 1-10 | 監査キット完成/開拓リスト20件/監査ページ1枚公開/本システム稼働 | WF-08(自己監査=Client Zero含む) |
| Phase B: 開拓 | 8-30 | 週5件接触/無料相談3件以上/**有償監査1件目受注** | WF-01, 02, 03 |
| Phase C: 診断 | 25-45 | 監査実施→報告→提案(監査→次段転換に挑む) | WF-04, 05 |
| Phase D: 転換 | 40-60 | **初回有償クライアント確定**(監査受注時点で目標達成。L3/L4成約は上振れ)/2件目パイプライン | WF-05, 06, 07 |
| 常時 | 1-60 | 毎日のSTATE.md更新/週次レビュー/収穫 | WF-08, VERIFICATION.md |

**成功の定義:** 有償監査の入金1件=「最初の有償クライアント」達成。60日でL4(本体構築)まで到達すれば大幅な上振れ。

## 6. 起動方法(Day 1にやること)

1. 本リポジトリをGitHubに作成し、6ファイルとフォルダ構成を配置する
2. STATE.mdの初期値(Day 0の現状)を人間が記入する
3. Claude Codeで `/morning` (朝会コマンド: STATE.md読込→当日タスク提案→最終判断ルールで選別)を実行する
4. Phase Aの最初のタスク「監査キットの組立(WF-08)」から着手する

## 7. 将来統合(設計済みの接続先)

- **GitHub:** 本リポジトリそのもの(Day 1から使用)
- **n8n:** WF-02(受付自動化)・WF-07(フォロー自動化)が最初の移植先。各WFの「将来自動化」欄に接続仕様を記載済み
- **MCP:** CRM・メール・カレンダーとエージェントの接続標準。leads/台帳→CRM移行時にMCP経由へ
- **CRM:** leads/_pipeline.mdが暫定CRM。リード20件超またはPhase C到達で専用CRMへ移行(台帳形式は移行を前提に設計済み)

**本書の思想:** これは静的な文書ではなく、logs/とskills/が毎週太っていく生きたOSである。60日後、このリポジトリ自体が「PHOSARAの最初のD4商品(エージェント企業システム)のプロトタイプ」になる。
