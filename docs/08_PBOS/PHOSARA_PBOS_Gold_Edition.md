# PHOSARA Business Operating System(PBOS)
## 設計書 — v1.0 → v2.0 → Gold Edition(完全版)

**位置づけ:** PHOSARAの収益を生成する事業オペレーティングシステムの設計書
**設計原理:** フローで設計する(人で設計しない)
**第一原理:** すべての工程は「60日以内の収益に寄与する」か「再利用可能なPBOS資産になる」かの少なくとも一方を満たすこと
**既存資産との接続:** Business_Audit_Guide v1.0 / 監査テンプレート4種(事業・デザイン・Web・ブランディング)/ Company OS v1.0 / 改善仕様書 v1.0

---

## 0. 三つの概念の分離(最初に固定する)

本設計の前提として、混同されやすい3概念を分離する。

| 概念 | 正体 | PBOSとの関係 |
|---|---|---|
| **PBOS** | 収益を生む業務の流れ(何が、どの順で、どんな基準で流れるか) | 本体 |
| **Webサイト** | 見込み客がPBOSに入ってくる**入口** | PBOSの第1ステージに接続される装置。PBOSそのものではない |
| **自動化(n8n/MCP等)** | PBOSの各ステージを**実行**する筋肉 | PBOSが決めた流れを高速化する。流れは決めない |
| **AI Company(Company OS)** | PBOSを**運転**する主体(人間+エージェントの編成と規律) | 誰が・どの権限で・どの品質でPBOSを回すかを定める |

一文で言えば——**PBOSは楽譜、Webサイトは客席の入口、自動化は楽器、AI Companyは演奏者**である。楽譜を先に書く。本書がその楽譜である。

# 第1部 PBOS v1.0(初期設計)

## 1.1 基本フロー

既存の営業フロー定義(Business Audit Guide:無料相談→事業監査→デザインコンサル→提案→制作→改善)を骨格として、前後を拡張した14ステージの線形フローを初期案とする。

```
[S1] 問い合わせ(Inquiry)
  ↓
[S2] 無料相談(Free Consultation)
  ↓
[S3] 事業監査(Business Audit)※既存テンプレート4種を使用
  ↓
[S4] 分析・優先課題の特定(Analysis)
  ↓
[S5] 提案(Proposal)
  ↓
[S6] 契約(Contract)
  ↓
[S7] 制作(Production)
  ↓
[S8] レビュー・品質検査(Review)
  ↓
[S9] 納品(Delivery)
  ↓
[S10] 事例化(Case Study)
  ↓
[S11] SEO・コンテンツ公開
  ↓
[S12] SNS発信
  ↓
[S13] 紹介依頼(Referral)
  ↓
[S14] CRM・リピート営業
```

## 1.2 v1.0の設計意図

- 診断(監査)を制作の前に置く既存メソドロジー(Diagnosis → Proposal → Creative Production → Improvement)を忠実にフロー化した。
- 納品後に事例化→発信→紹介と続け、次の問い合わせを生む「後工程」を明示した。

# 第2部 セルフレビュー第1回 — v1.0の弱点分析

審査基準(論理矛盾/欠落工程/重複/ボトルネック/収益漏出/顧客体験/自動化機会/属人依存/拡張性/再利用性)でv1.0を検査した結果、**構造的欠陥8件**を検出した。

| # | 弱点 | 分類 | 内容 |
|---|---|---|---|
| W1 | **環がない(線形の死)** | 構造欠陥 | S14で止まる一本道。事例→SEO→問い合わせという環、リピート→再監査という環が構造化されておらず、毎回ゼロから客を探す設計になっている |
| W2 | **最初の収益点が遠すぎる** | 収益漏出 | S6(契約)まで無報酬。S3の監査——PHOSARA最大の独自価値——を無償で配る設計は、60日収益の第一原理と矛盾し、監査の価値も毀損する。**監査は最初の有償商品にすべき** |
| W3 | **選別(Qualification)工程がない** | 欠落工程 | 無料相談に誰でも入れる設計では、アンチICP(価格のみで選ぶ客・美学に敬意のない客)に監査工数を浪費する。Company OS改善仕様C-03と不整合 |
| W4 | **「今じゃない」客の受け皿がない** | 収益漏出 | 相談後・提案後に成約しなかった見込み客が捨てられる。半年後に買う客が最も安い獲得コストの客なのに、育成(ナーチャリング)工程が存在しない |
| W5 | **継続収益の段がない** | 収益漏出(最大) | S9納品で関係が切れる。運用・保守・改善・自動化という月額継続(リテイナー)への接続がなく、LTVが単発案件で頭打ちになる |
| W6 | **入口がWebサイト頼み** | 論理矛盾 | 自社サイトは未完成でSEOは効き始めるまで数ヶ月かかる。S1が「問い合わせを待つ」設計では60日目標が運任せになる。初動用の能動チャネルが欠落 |
| W7 | **事例化が偶然任せ** | 再利用性 | S10の事例化はクライアント承諾に依存するが、承諾を得る仕組み(契約時の収穫条項=改善仕様C-09)がフローに組み込まれていない |
| W8 | **資産化の視点が後工程に偏在** | 再利用性 | 第一原理の「PBOS資産になる」は全ステージの義務のはずが、v1.0ではS10〜S12のみが資産を生む設計。監査・提案・制作の途中産物(テンプレート・文例・部品)が捨てられる |

**結論:** v1.0は「既存メソドロジーの直列化」としては正しいが、**環・収益点・選別・継続**を欠く。全面再設計する。

# 第3部 PBOS v2.0(再設計)

## 3.1 構造転換: 一本道から「二重ループ+梯子」へ

v2.0は3つの構造を導入する。

### 構造1: 二重ループ(Revenue Loop × Asset Loop)

```
        ┌──────────── 収益ループ(表舞台)────────────┐
        │                                            │
 需要 → 選別 → 有償監査 → 提案 → 契約 → 制作 → 納品 → 継続運用
  ▲                                            │       │
  │                                            ▼       ▼
  │      ┌──────── 資産ループ(裏舞台)────────┐  リピート・追加案件
  └──────┤ 事例・知識・テンプレート・部品の収穫 │◀──(全ステージから)
         │ → 発信(SEO/SNS)→ 紹介 → 需要へ還流  │
         └────────────────────────────────────┘
```

- **収益ループ:** 顧客が流れる。1周ごとに売上を生む。
- **資産ループ:** 知識が流れる。1周ごとに「次の1周を安く・速く・強くする資産」を生む。収穫は納品後だけでなく**全ステージの出口で行う**(W8の解消)。

### 構造2: オファーラダー(LIGHT Ladder)

単発取引を段階的な関係に変える商品の梯子。上の段ほど単価と継続性が高い。

| 段 | 商品 | 性質 | 収益型 |
|---|---|---|---|
| L1 | **無料相談**(30〜45分) | 選別と信頼の入口。売らない、診る | ¥0(選別装置) |
| L2 | **事業監査**(有償) | 最初の商品。テンプレート4種による診断+優先課題+方向性 | 単発・低額(買いやすい価格) |
| L3 | **解決スプリント** | 監査の最優先課題1点を短期集中で解く(例: ブランド核の言語化、LP1枚) | 単発・中額 |
| L4 | **本体構築** | サイト・ブランド・仕組みの本格構築(LIGHT Process適用) | 単発・高額 |
| L5 | **継続運用(Run)** | 保守・改善・レポート・小規模制作の月額 | **継続(MRR)** |
| L6 | **自動化・AI導入(Scale)** | n8n/AIエージェントによる業務自動化。D3/D4商品 | 継続+単発 |

**梯子の規律:** どの段からでも降りられる(押し売りしない)が、各段の納品物は必ず次の段への「自然な問い」を含んで終わる(監査は方向性で終わり、方向性は「では誰が作るか」を問う)。

### 構造3: 需要エンジン3チャネル(W6の解消)

| チャネル | 性質 | 効き始め | 60日目標への寄与 |
|---|---|---|---|
| CH1 直接開拓 | 既存の縁・地域の対象業種(建設/リフォーム/クリニック/ホール)への監査提案 | 即日 | **主力** |
| CH2 作品・知識公開 | 自社サイト(PXD実証)+事例+診断知識の発信(SEO/SNS) | 3〜6ヶ月 | 種まき |
| CH3 紹介システム | 監査納品時・案件完了時の紹介依頼の定型工程化 | 1周目の完了後 | 2件目以降 |

## 3.2 v2.0フロー(17ステージ)

```
【需要】 D1 需要創出(CH1/CH2/CH3) → D2 問い合わせ受付
【選別】 Q1 適格判定 → Q2 無料相談 →(不適格→CRM育成へ)
【診断】 A1 有償監査の受注 → A2 監査実施 → A3 分析・報告
【転換】 P1 提案 → P2 契約(収穫条項込み)
【制作】 B1 制作(LIGHT) → B2 品質検査 → B3 納品
【継続】 R1 継続運用(Run/Scale) → R2 定期レビュー → 追加案件へ還流
【資産】 H1 収穫(全ステージ出口) → H2 事例化・発信 → H3 紹介依頼 → D1へ還流
【育成】 N1 CRM・ナーチャリング(不成約・保留客) → 再接触 → Q1へ還流
```

# 第4部 セルフレビュー第2回 — v2.0の弱点分析

v2.0を同じ基準で再検査した結果、**運用上の欠陥6件**を検出した(構造は妥当、制御系が不足)。

| # | 弱点 | 内容 |
|---|---|---|
| W9 | **監査の無料コンサル化リスク** | 有償監査の場で解決策まで語ってしまうと、L3以降を買う理由が消える。「監査は方向まで、解決策はデザインコンサルから」という既存規律(Business Audit Guide P19)を、フロー上のスコープ管理として明文化する必要 |
| W10 | **判断点渋滞** | 人間1人の初期体制で、Q2相談・A2監査・P1提案・B2検査のすべてがLevel H(人間必須)。同時案件数の上限(WIP制限)がないと品質か納期が崩壊する。Company OS改善仕様I-09と同じ問題 |
| W11 | **価格ガバナンスの不在** | 各段の価格決定基準がない。場当たりの値付けは「灯した光の価値で決める」(経済原則)と矛盾し、疲弊型の安売りを招く |
| W12 | **キャッシュフローの谷** | L4本体構築は工期が長い。着手金・中間金の設計がないと、受注しているのに現金がない状態が起きる |
| W13 | **KPIにオーナーがいない** | 測る数字は定義したが「誰が・どこで・いつ見るか」が未定義。計測されないKPIは存在しないのと同じ |
| W14 | **単一顧客依存の無警戒** | 初期は1〜2社に売上が集中しがち。依存度の監視と分散の規律が必要(経済原則18-4と接続) |

**結論:** v2.0の構造(二重ループ+梯子+3チャネル)は維持し、**制御系(スコープ・WIP・価格・現金・計測・分散)を実装してGold Editionとする。**

## 5.2 全ステージ仕様(目的・入力・出力・判定基準・KPI・人間の判断・AIの責務・自動化機会)

### 【需要ブロック】

**D1 需要創出**
- 目的: 適格な見込み客との接点を、3チャネルで継続的に発生させる
- 入力: 事例・知識資産(資産ループから)/ 対象業種リスト(建設・リフォーム・クリニック・ホール)
- 出力: 問い合わせ・相談申込
- 判定基準: CH1は「監査を提案できる具体的接点か」/ CH2は「知識の開示階層(公開可)に適合するか」
- KPI: 月間新規接点数、チャネル別問い合わせ数
- 人間の判断: 開拓先の選定、発信内容の最終承認(ブランドトーン)
- AIの責務: 開拓先候補のリスト化と下調べ(ChatGPT/Claude)、発信文の下書き、SEO記事の草稿
- 自動化機会: SNS予約投稿(n8n)、開拓リストの管理(CRM)、サイト計測(GA→n8n→月次集計)

**D2 問い合わせ受付**
- 目的: 全接点(フォーム・メール・電話・紹介)の問い合わせを一箇所に集約し、24時間以内に一次応答する
- 入力: 問い合わせ(サイトフォーム/メール/紹介)
- 出力: CRM上のリード記録+一次返信+相談日程候補
- 判定基準: 全項目(社名・業種・課題感・きっかけ)が揃っているか。不足時は追加質問を返す
- KPI: 一次応答時間(目標: 営業日24時間以内)、取りこぼし0件
- 人間の判断: なし(定型)
- AIの責務: 問い合わせ内容の構造化・要約・業種分類(Intake Agent)
- 自動化機会: フォーム→CRM自動登録→一次返信→日程調整リンク送付まで全自動(n8n+メール+カレンダー)。**PBOS内で最初に完全自動化すべき工程**

### 【選別ブロック】

**Q1 適格判定(Qualification)**
- 目的: 監査工数を投じる価値がある相手かを、相談前に判定する
- 入力: D2のリード記録+AIの下調べ(サイト・発信の現状確認)
- 出力: 適格/育成行き/辞退 の3分類
- 判定基準(適格の条件・すべて満たす): (1)対象業種または近接業種で意思決定者に会える (2)価格ではなく課題を語っている (3)診断→改善という順序を受け入れる素地がある。アンチICP(値段だけ・美学への敬意なし・丸投げ体質)は丁重に育成行きか辞退
- KPI: 相談実施率、相談→監査転換率(選別が機能していれば高くなる)
- 人間の判断: 3分類の最終判定(Level H)
- AIの責務: 判定材料の整理(現状サイトの簡易スキャン、業種・規模の確認)
- 自動化機会: 判定材料パッケージの自動生成(n8n: リード登録→AI下調べ→判定シート添付で人間に通知)

**Q2 無料相談(30〜45分)**
- 目的: 売らずに診る。信頼の獲得と、有償監査への自然な接続
- 入力: 適格リード+判定材料パッケージ
- 出力: 相談記録+監査提案(するか否かの判断)
- 判定基準: 相談の出口で「課題は監査に値する深さか」「予算・時期の現実性はあるか」を判定。**この場で解決策を語らない**(W9対策: 相談は課題の輪郭まで)
- KPI: 相談→監査受注率(目標: 50%以上。低ければQ1の選別が甘い)
- 人間の判断: 相談実施そのもの、監査提案の判断(Level H)
- AIの責務: 相談メモの構造化、相談後フォローメールの下書き
- 自動化機会: 日程調整・リマインド・議事メモ整理・お礼メール送付(カレンダー+n8n+AI)

### 【診断ブロック】(最初の収益点)

**A1 有償監査の受注**
- 目的: PBOSの最初の売上を立てる。監査を「無料の営業活動」から「商品」に転換する
- 入力: Q2の相談記録
- 出力: 監査申込+入金確認+実施日程
- 判定基準: 監査範囲の合意(事業監査を基本とし、必要に応じWeb/ブランディング/デザイン監査を追加)。**入金確認を実施の条件とする**(W12対策)
- KPI: 監査受注数(60日目標の中心KPI)、監査単価
- 人間の判断: 範囲と価格の提示(価格ガバナンス: 5.4参照)
- AIの責務: 申込書・請求書の生成
- 自動化機会: 申込→請求→入金確認→日程確定→事前ヒアリングシート送付(n8n+会計/決済+メール)

**A2 監査実施**
- 目的: テンプレート4種に基づく構造的診断(三つの証拠源: 観察・対話・資料)
- 入力: 事前ヒアリングシート+既存接点(サイト・SNS・販促物)+対話
- 出力: 記入済み監査テンプレート(6領域スコア+エビデンス)
- 判定基準: 全領域に複数証拠源のエビデンスがあるか。スコアは優劣でなく優先度の可視化(既存ガイド準拠)
- KPI: 監査リードタイム(受注→報告までの日数)
- 人間の判断: ヒアリング実施、スコアの確定(Level H)
- AIの責務: 事前の観察パート(サイト・発信の予備診断)を下書き、対話記録の整理、証拠の突き合わせ支援
- 自動化機会: Webサイト監査の技術項目(速度・モバイル・SEO基礎・リンク切れ)の自動計測(Claude Code/ツール→テンプレートへ自動転記)

**A3 分析・報告**
- 目的: 診断を「最も効く一点」に絞り込み、方向性として提示する(解決策には踏み込まない)
- 入力: 記入済みテンプレート
- 出力: 監査報告書(サマリー+スコア+優先課題+戦略的方向性+次の一手)※既存の成果物5点構成に準拠
- 判定基準: 優先課題が1点に絞られているか/方向と解決策が分離されているか/報告書がPHOSARAのトーン(静かで明晰)を保っているか
- KPI: 監査→次段(L3/L4)転換率(目標: 40%以上)
- 人間の判断: 優先課題の最終確定、報告プレゼン(Level H)
- AIの責務: 報告書ドラフト生成(テンプレート→報告書の整形)、類似過去事例の想起
- 自動化機会: テンプレート→報告書PDFの生成パイプライン(GitHub+Claude Code)。**監査のたびに磨かれるPBOS中核資産**

### 【転換ブロック】

**P1 提案**
- 目的: 監査の方向性を、具体的な解決策と投資額に翻訳する(デザインコンサルティングの入口)
- 入力: 監査報告書(優先課題+方向性)
- 出力: 提案書(解決策・範囲・価格・工程・体制)
- 判定基準: 提案が監査の優先課題1点に対応しているか(監査にない課題を突然売らない)/ 梯子のどの段(L3スプリント or L4本体)が適切か
- KPI: 提案→成約率(目標: 50%以上)、平均提案額
- 人間の判断: 解決策の設計と価格(Level H・Type 2決定として記録)
- AIの責務: 提案書ドラフト、見積の根拠資料、過去類似案件の実績参照
- 自動化機会: 提案書テンプレートの部品化(GitHub)、送付・閲覧追跡・期日リマインド(n8n)

**P2 契約**
- 目的: 法的リスクなく着手できる状態を作り、資産ループの権利を確保する
- 入力: 合意済み提案
- 出力: 締結済み契約+着手金入金
- 判定基準: **必須条項3点**——(1)収穫条項(一般化した知見・手法・部品の再利用権はPHOSARAが保持) (2)事例化条項(匿名化/実名の別を明記) (3)支払条件(着手金50%・納品時50%を基本形)。W7・W12の恒久対策
- KPI: 契約リードタイム、着手金回収率100%
- 人間の判断: 契約締結(Level H・Type 1に準じる慎重さ)
- AIの責務: 契約書ドラフト(テンプレートから)、条項チェックリスト照合
- 自動化機会: 電子契約送付→締結→請求→入金確認→キックオフ日程(n8n)

### 【制作ブロック】

**B1 制作(LIGHT Process適用)**
- 目的: 契約範囲をPXD品質で実装する(Company OSのL-I-G-H-Tに接続: 傾聴・照明は監査・提案で完了済み→Generateから)
- 入力: 契約+提案書+監査報告書(ブリーフとして)
- 出力: 制作物(サイト/ブランド/仕組み)
- 判定基準: 監査で定めた方向性との整合(逸脱時は人間が判断して記録)
- KPI: 制作リードタイム、人間工数/案件(計測ベースライン)
- 人間の判断: コンセプト整合の中間レビュー、美学の最終調整(Level H)
- AIの責務: 実装の主力(Claude Code: コーディング、WordPress構築、コンテンツ下書き)
- 自動化機会: 開発環境の定型セットアップ、部品ライブラリ(GitHub)からの再利用、ステージング自動デプロイ

**B2 品質検査**
- 目的: Company OS品質4層(技術的完全性/工芸的精度/体験の一貫性/光の検査)の通過
- 入力: 制作物
- 出力: 検査記録+合格判定
- 判定基準: Layer1-2はチェックリスト全項目、Layer3-4は人間判断。**不合格品は納期圧力があっても出荷しない**
- KPI: 一発合格率、検出不具合数(チェックリスト改訂の材料)
- 人間の判断: Layer3(体験一貫性)・Layer4(光の検査)(Level H)
- AIの責務: Layer1の自動検査(速度・レスポンシブ・リンク・アクセシビリティ)、Layer2の規則照合
- 自動化機会: 技術検査の完全自動化(QA Agent化の第一候補)

**B3 納品**
- 目的: 引き渡しと、継続段(R1)への接続
- 入力: 合格した制作物
- 出力: 納品物+操作説明+**継続運用の提案書(必ず添える)**
- 判定基準: 顧客が自走できる最低限の引き継ぎが完了しているか/継続提案が「売り込み」でなく「納品物の価値を保つ手段」として提示されているか
- KPI: 納品→継続契約転換率(目標: 60%以上。**PBOS最重要KPIの一つ**)
- 人間の判断: 納品判断(Level H)、継続提案の内容
- AIの責務: 操作マニュアル生成、継続提案書ドラフト
- 自動化機会: 納品パッケージ(認証情報・マニュアル・保証範囲)の定型生成

### 【継続ブロック】(MRRの源泉)

**R1 継続運用(Run/Scale)**
- 目的: 月額継続収益の獲得と、顧客事業への継続的関与(次の案件の種はここで見つかる)
- 入力: 継続契約
- 出力: 月次の保守・改善・レポート/(Scale)自動化・AI導入の実装
- 判定基準: 契約範囲の遵守(スコープ外は追加提案として切り出す)
- KPI: **MRR(月次継続収益)**、解約率、顧客あたり追加案件数/年
- 人間の判断: 改善提案の内容、関係性の維持(Relation Keeper役割)
- AIの責務: 監視・バックアップ・定期メンテ(Ops Agent)、月次レポート生成(Report Agent)
- 自動化機会: 監視→異常検知→通知、月次レポートの全自動生成・送付(n8n+AI)。**Level A化の最有力領域**

**R2 定期レビュー(四半期)**
- 目的: 成果の確認と、梯子の次の段(追加スプリント・自動化・再監査)への還流
- 入力: 月次レポート蓄積+顧客の事業変化
- 出力: レビュー記録+次の提案(該当時)
- 判定基準: 数字(サイト成果)と対話(事業の変化)の両方を見る
- KPI: レビュー実施率100%、レビュー→追加案件転換率
- 人間の判断: レビュー面談、追加提案の判断
- AIの責務: レビュー資料の自動生成(1年分の推移含む)
- 自動化機会: 四半期ごとの資料生成→日程調整の自動起票

### 【資産ブロック】(裏舞台・複利の源泉)

**H1 収穫(Harvest)— 全ステージの出口で実施**
- 目的: 経験を再利用可能資産に変換する(第一原理の後半を全工程で担保)
- 入力: 各ステージの成果物・気づき・失敗
- 出力: GitHub上の資産——監査の業種別知見/提案・契約の文例/制作部品/チェックリスト改訂/Incident記録
- 判定基準: 「次に同じ状況が来たら、何を再利用するか」に答えられる形か/顧客機密は匿名化・一般化されているか(契約の収穫条項の範囲内か)
- KPI: 案件あたり収穫件数、資産の再利用率(次案件で使われた率)
- 人間の判断: 何を資産化するかの選定
- AIの責務: 収穫候補の自動抽出(Librarian Agent: 「この案件で新しかったことは何か」の棚卸し支援)、整形・タグ付け
- 自動化機会: 案件クローズ時の収穫チェックリスト自動起票(n8n)、リポジトリへの構造化格納

**H2 事例化・発信**
- 目的: 収穫物を需要創出の弾薬に変換する(CH2の燃料)
- 入力: 収穫された事例素材(契約の事例化条項に基づく)
- 出力: 事例ページ(自社サイト)、SEO記事、SNS投稿
- 判定基準: 知識の開示階層(公開可/商品/秘匿)の判定/ブランドトーン検査(静かな強度——実績を騒がずに示す)
- KPI: 月間公開数、事例経由の問い合わせ数
- 人間の判断: 公開可否とトーンの最終承認(Level H)
- AIの責務: 事例記事・投稿文の下書き、SEOキーワード調査
- 自動化機会: 下書き生成→承認→WordPress公開→SNS配信のパイプライン(n8n+WordPress API)

**H3 紹介依頼**
- 目的: 満足の瞬間を次の需要に変換する(CH3)
- 入力: 監査報告時・納品時・成果確認時(3つの「満足の頂点」)
- 出力: 紹介(D2へ還流)
- 判定基準: 依頼は定型工程として必ず実施(気が向いたらではなく、フローに組み込む)。「同じ課題で困っている同業・知人はいませんか」の一問
- KPI: 紹介発生率、紹介経由成約数
- 人間の判断: 依頼のタイミングと言い方(関係性判断)
- AIの責務: 紹介用の一枚資料(監査の紹介パンフ)の維持
- 自動化機会: 納品後30日のフォローメールに紹介導線を定型組み込み(n8n)

### 【育成ブロック】

**N1 CRM・ナーチャリング**
- 目的: 「今じゃない」客を捨てずに、時が来たら最初に想起される位置を保つ(W4の恒久対策)
- 入力: 不成約リード・保留客・過去客
- 出力: 定期的な価値接触(知識コンテンツ・事例・年賀等)→再相談(Q1へ還流)
- 判定基準: 接触は売り込みでなく価値提供(発信物の共有)/接触頻度は四半期に1回程度(静かな強度)
- KPI: 育成リード数、育成→再相談の転換数/年
- 人間の判断: 個別の再接触判断
- AIの責務: リードの状態管理、再接触タイミングの提案、接触文面の下書き
- 自動化機会: CRMステータス管理+四半期接触の自動起票(n8n)。**手動運用が最も破綻しやすい工程のため、初期から自動化必須**

## 5.3 制御系(Gold Editionで追加された規律)

**WIP制限(W10対策):** 同時進行の上限を「監査2件+制作1件+継続運用N件」とする(初期の人間1名体制)。上限超過時は受注を止めるか開始日を後ろにずらす。判断能力を出荷制約として扱う。

**価格ガバナンス(W11対策):** 各段の価格は「価格表」としてGitHubで管理し、変更はType 2決定として記録する。値引きは原則行わず、予算が合わない場合は範囲(スコープ)を削る。監査価格は「支払いに覚悟が要るが、決裁者が即断できる」帯に設定する。

**現金規律(W12対策):** 監査=前払い、制作=着手金50%。入金確認が着手条件。

**計測の所在(W13対策):** 全KPIはCRMとGitHub上の案件記録から月次で自動集計し(Report Agent/n8n)、月初に人間が15分で確認する「月次計器盤」を定例化する。見る日が決まっていない数字は存在しないのと同じ。

**分散規律(W14対策):** 単一顧客の売上依存度30%超で警告、40%超で新規開拓を最優先化する。

**スコープ規律(W9対策):** 監査の場で解決策を聞かれたら「それは次の工程で設計します。今日は課題を正しく定めることに集中します」と答える——この一文自体をPlaybook化する。

# 第6部 三つの関係(Webサイト・自動化・AI Company)

## 6.1 Webサイトとの関係 — 「入口」としての設計要求

WebサイトはPBOSではない。**PBOSのD1〜D2(需要→受付)に接続される入口装置**である。この位置づけから、自社サイトへの設計要求が逆算される。

| PBOS上の要求 | サイトへの実装要求 |
|---|---|
| 適格な客を呼び、不適格な客を自然に遠ざける(Q1の負荷軽減) | 価格帯・進め方(診断から始める)・美学を隠さず提示する。「安く早く」を求める客が自分から合わないと気づく設計 |
| 監査(L2)という入口商品に着地させる | サイトの主CTAは「制作のお見積り」ではなく**「無料相談→事業監査」**。監査の価値説明ページを中核に置く |
| PXDの実証第1号として機能する(CH2の最強の弾) | 黒背景・赤の核・一本の光の線・シネマティックイントロ——サイト自体が「PHOSARAに頼むとこうなる」の生きた見本 |
| 問い合わせをD2に構造化して渡す | フォーム項目=Intake Agentの入力仕様(業種・課題感・きっかけ・時期)。フォーム→CRM→一次返信の自動接続 |
| 資産ループの出力先(H2) | 事例・知識記事の受け皿となる情報設計を初版から持つ(後付けにしない) |

## 6.2 自動化との関係 — 自動化マップ

自動化はPBOSではない。**PBOSの各ステージを実行する筋肉**である。ツール別の配置は以下の通り。

| ツール | PBOS上の持ち場 |
|---|---|
| **WordPress** | 入口(自社サイト)+H2の公開基盤+顧客納品物(D1商材) |
| **CRM** | D2受付〜N1育成の全リード状態管理。PBOSの「現在地」を映す台帳 |
| **n8n** | ステージ間の接続配管: フォーム→CRM→返信、申込→請求→入金→日程、納品→フォロー→紹介、四半期接触の起票、KPI集計 |
| **メール** | D2一次返信・A1請求・N1育成接触の配送路(n8nから駆動) |
| **カレンダー** | Q2相談・A2監査・R2レビューの日程調整(調整リンク+リマインド自動化) |
| **Claude Code** | B1制作の主力実行者+A2技術監査の自動計測+H2生成パイプラインの構築 |
| **ChatGPT/Claude** | D1下調べ・Q1判定材料・A3報告書ドラフト・P1提案ドラフト・H1収穫整理などの生成系全般 |
| **GitHub** | 資産ループの保管庫: テンプレート・価格表・Playbook・部品・事例素材・KPI記録 |
| **MCP** | 上記ツール群とAIの接続標準(将来のエージェント化の配線) |

**自動化の優先順位(60日視点):** ①D2受付の全自動化(取りこぼし0)→ ②A1申込〜入金の配管 → ③N1育成の状態管理 → ④A3報告書生成パイプライン → ⑤R1監視・レポート(継続客が生まれてから)。

## 6.3 AI Companyとの関係 — 「運転者」としての分離

AI CompanyはPBOSではない。**PBOSを運転する主体の設計**(=Company OS)である。両者の分離は次の通り。

| 問い | 答える文書 |
|---|---|
| 何が、どの順で流れ、どこで金が生まれるか | **PBOS(本書)** |
| 誰が(人間/どのエージェントが)、どの権限(H/R/A)で各ステージを担うか | **Company OS**(組織構造・協働ポリシー) |
| どの品質で通すか | **Company OS**(品質4層)をPBOSのB2・A3が呼び出す |
| どう実行するか | **自動化層**(n8n/Claude Code/MCP) |

PBOS��各ステージに記した「人間の判断/AIの責務」は、Company OSのエージェント編成(Intake/Research/Build/QA/Ops/Report/Librarian)への発注仕様である。つまり——**PBOSが職務記述書を書き、Company OSが働き手を供給し、自動化層が道具を渡す。**

# 第7部 リスク・将来サービス・将来拡張

## 7.1 潜在リスク

| リスク | 兆候 | 対策(PBOS内) |
|---|---|---|
| 監査が売れない(入口商品の不発) | 相談→監査転換率が30%未満が続く | 価格・範囲の再設計/監査の一部(簡易診断)を無料相談に前出しして価値を先に見せる/CH1の対象再選定 |
| 監査止まり(L3以降に進まない) | 監査→次段転換率が20%未満 | A3報告の「次の一手」の精度検証/優先課題が大きすぎないか(スプリントで買える粒度に分解) |
| 制作ボトルネック | 制作リードタイム超過・WIP上限常時到達 | 部品再利用率の向上/Claude Code活用度の点検/受注ペース調整 |
| 属人依存(全Level Hが1人) | 判断待ち時間の増大 | 判断点の棚卸し→R昇格候補の特定(実績3回ルール)/Company OS I-09と連動 |
| 継続契約が積み上がらない | 納品→継続転換率50%未満 | B3の継続提案を「オプション」から「標準構成」へ(継続前提の見積提示) |
| 単一顧客依存 | 依存度30%超 | 分散規律の発動(新規開拓の最優先化) |
| 無料相談の消耗化 | 不適格相談の増加 | Q1判定基準の厳格化/サイトでの事前期待値設計 |
| 資産ループの形骸化 | 収穫0件の案件クローズ | 収穫チェックリストをクローズの必須条件に(儀式でなく関門にする) |

## 7.2 将来サービス機会(PBOSが生む商品の種)

PBOS��回すこと自体が、次の商品を生む。

1. **業種別監査エディション** — 監査実績が業種知見として蓄積→「建設業版事業監査」等のパッケージ化(既存ガイドの将来展開と一致)
2. **セルフ診断ツール** — 監査テンプレートの簡易版をWeb化(入口商品の下にもう一段安い段を作る+リード獲得装置)
3. **監査つき保守(Audit-in-Run)** — R1継続運用に年1回の再監査を組み込んだ上位プラン
4. **自動化導入パッケージ(L6の商品化)** — 自社PBOSで実証済みのn8n構成を業種別に展開(Dogfooding原則の換金)
5. **PBOS-as-a-Service** — 本書の方法論そのもの——診断から継続までの事業OS設計——を他の小規模事業者に提供(Company OS Phase 3「方法論の外販」の先行形。ただし売るのは方式のみ、蓄積は売らない)
6. **エージェント運用代行** — R1で稼働するOps/Report Agentの構成を、顧客側業務に展開(D4事業の入口)

## 7.3 将来拡張(5〜10年視点)

- **拡張の順序:** 深化(監査→戦略の上流化)→ 横展開(業種エディション)→ プロダクト化(セルフ診断・テンプレート)→ 方法論外販(PBOS/Company OS)。Company OS第16章の拡張判定(3条件AND)に従う。
- **不変の核:** どれだけ拡張しても「診断が先、制作が後」「収穫なきクローズなし」「継続への接続を標準装備」の3原則は変えない。これがPBOSの背骨である。
- **技術交代への備え:** PBOSはツール名を含まない層(ステージ・判定基準・KPI)と、ツール名を含む層(6.2自動化マップ)を分離して記述してある。ツールが世代交代しても、本書の第5部は書き換え不要である。

# 最終レポート

## Executive Summary

PBOS��、PHOSARAの収益を生む事業オペレーティングシステムである。v1.0(既存メソドロジーの直列化)の構造的欠陥8件、v2.0(二重ループ+梯子)の運用的欠陥6件を自己審査で検出・解消し、Gold Editionとして完成させた。核心は3つ——**(1) 有償の事業監査を最初の収益点とする**(既存の監査資産4種を商品化し、60日以内の売上を診断で立てる)。**(2) 収益ループと資産ループの二重構造**(1周ごとに売上と再利用資産の両方を生み、周回のたびに速く・安く・強くなる)。**(3) オファーラダーによる継続収益化**(監査→スプリント→構築→月額運用→自動化と、単発をMRRに転換する梯子)。

## PBOS Architecture

需要(3チャネル)→ 選別(適格判定+無料相談)→ 診断(有償監査=最初の売上)→ 転換(提案・契約)→ 制作(LIGHT)→ 継続(Run/Scale=MRR)の収益ループに、全ステージから収穫する資産ループ(収穫→事例化→発信→紹介→需要へ還流)と、不成約客の育成ループ(CRM→再相談)が絡む三重環構造。制御系としてWIP制限・価格ガバナンス・現金規律・月次計器盤・分散規律・スコープ規律を装備する(第5部)。

## Revenue Flow

収益点は3つ。**①監査売上**(前払い・短サイクル——60日目標の主力)、**②構築売上**(着手金50%+納品時50%——キャッシュの谷を作らない)、**③継続売上MRR**(運用・改善・自動化——LTVの主成分)。最重要転換KPIは「相談→監査50%」「監査→次段40%」「納品→継続60%」の3点。この3つの率が、PBOSの健康診断そのものである。

## Automation Map

n8n=ステージ間の配管(受付・請求・育成・集計)、Claude Code=制作と技術監査の実行、ChatGPT/Claude=全生成系の下書き、CRM=リードの現在地台帳、WordPress=入口と公開基盤、GitHub=資産ループの保管庫、カレンダー/メール=日程と配送、MCP=将来のエージェント配線。優先自動化は①問い合わせ受付の完全自動化 ②監査の申込〜入金配管 ③育成CRMの状態管理(詳細は6.2)。

## AI Company Integration

PBOS��「何を」を定め、Company OSが「誰が・どの権限で」を定め、自動化層が「どうやって」を担う。PBOS各ステージの「人間の判断/AIの責務」欄は、Company OSのエージェント編成(Intake/Build/QA/Ops/Report/Librarian)への職務発注仕様であり、両文書はこの欄で接続される。人間の判断点(Level H)は相談・監査確定・提案価格・契約・品質Layer3-4・納品・公開承認に集約し、それ以外は段階的にR/Aへ昇格させる。

## 最後の問いへの回答 — 「PBOS完成後、PHOSARAは次に何を作るべきか?」

**「クライアント・ゼロ計画」——PHOSARA自身を最初の監査対象にして、PBOSを一周させること。** 具体的な成果物は2つ。

**1つ目は、有償監査の商品パッケージ(監査キット)。** 価格表・申込動線・事前ヒアリングシート・テンプレート4種の実施手順・報告書生成パイプライン——つまりPBOSのA1〜A3を「明日売れる」状態にした実弾。PBOSは設計図であり、最初に装填すべき弾はこれである。

**2つ目は、その弾を届ける最小の入口——自社サイト(まず監査ページ1枚から)。** ただし作る前に、PHOSARA自身に事業監査テンプレートを適用せよ。自社の価値・市場・顧客・ブランド・伝達・組織を、顧客にするのと同じ厳しさで診断し、その報告書を最初の公開事例(H2)にする。これは需要創出の弾薬であると同時に、「診断から始める会社が、自らを診断してみせる」という何よりの証明になる。

順序を一行で言えば——**監査キット → 自己監査(Client Zero)→ 監査ページ公開 → CH1開拓開始。** ドキュメントを作る段階は終わった。次は、PBOSの1周目を現実の売上で回す番である。
