# 01 文書管理の目的

PHOSARAの競争優位は、再現性にある。一度きりの成果ではなく、同じ品質で作り続けられる状態を提供する——この方針は、制作物だけでなく、それを支える文書にも等しく適用される。文書が散逸し、版が取り違えられ、同じ情報が複数の場所で食い違えば、再現性は失われる。

本書は、次の四点を目的とする。

- **一貫性を保つ。** すべての文書が、唯一の基準に従い、相互に矛盾しない状態を維持する。
- **属人化を防ぐ。** 誰が運用しても、同じ場所に、同じ規律で、同じ品質の文書が揃う状態をつくる。
- **再現性を支える。** 文書を、記憶や口頭ではなく、記録として接続する。工程が文書で再現できる状態を保つ。
- **資産として保全する。** 作成した文書を、版・出典・所在とともに管理し、長期にわたって参照可能な資産として残す。

文書管理は、整理整頓ではなく、事業の再現性そのものを担う基盤である。

# 02 適用範囲

本書は、PHOSARAが作成・保有・運用するすべての文書に適用される。媒体・形式（Markdown・HTML・Word・PDF・スライド等）を問わない。

**本書が適用される文書**

- ブランド基盤文書（理念・ポジショニング・ブランド規定）。
- 営業・コンサルティングの運用文書（プレイブック・各ガイド）。
- 実務で用いる記入式テンプレート。
- 業界別ソリューション・ケースブック・デザインシステムの設計文書。
- 案件ごとの記入済み文書・クライアント制作物。

**本書が定めること／定めないこと**

| 区分 | 内容 |
|---|---|
| 本書が定める | 文書の作成・保管・参照・命名・版管理・更新・廃止・品質・所有の規律。 |
| 本書が定めない | ブランドの中身（理念・ボイス・サービス）、各文書の内部の記入方法。これらは各文書が定める。 |

各文書の内部の詳細（診断の手法、テンプレートの記入欄、設計仕様の数値など）は、それぞれの文書に委ねる。本書は、文書間の関係と運用の規律に責任を持つ。

# 03 ドキュメント設計思想

PHOSARAの文書は、ブランドと同じ三つの柱——可視化・越境・本質——に従って設計する。設計思想は、次の原則に集約される。

- **唯一の基準を持つ。** すべての判断の源は一つである。理念・ポジショニング・ボイスは、唯一の基準に定義し、他の文書では再定義しない。
- **一つの情報は、一つの文書が管理する。** 同じ情報を複数の文書で重複して持たない。重複は、矛盾と更新漏れの温床である。
- **参照し、再定義しない。** 下位の文書は上位の文書を参照する。上位の定義を、下位で書き換えない。
- **削ることで強くする。** 文書も制作物と同じく、核以外を削ぐ。情報を詰め込まず、必要な一点を明確にする。
- **記録として接続する。** 工程・決定・成果は、口頭ではなく文書で残し、文書で次工程へ渡す。
- **再現可能に保つ。** 誰が見ても同じ場所・同じ規律・同じ版に辿り着ける状態をつくる。

この設計思想により、文書群は、量が増えても薄まらず、一貫した一つの体系として機能する。

# 04 ドキュメント階層


### ドキュメント関係図

```text
MASTER_CONTEXT
      │
      ▼
Guide（考え方）
      │
      ▼
Blueprint（設計）
      │
      ▼
Template（運用）
      │
      ▼
成果物
```

PHOSARAの文書は、四つの階層で構成する。階層は、文書の抽象度と参照の方向を定める。上位ほど普遍的かつ不変であり、下位ほど具体的かつ可変である。参照は常に下位から上位へ向かい、逆流しない。

```
階層0 ── 唯一の基準
         PHOSARA_MASTER_CONTEXT_v1.0_JP.md
              ↑（すべての文書がこれを参照する）
階層1 ── 基盤文書
         ブランド基盤（Brand Book・Wordmark Guidelines・Company Guide）
              ↑
階層2 ── 運用文書（Guide）
         考え方・原則・工程を定める（Playbook・各 Guide）
              ↑
階層3 ── 実務文書（Template）／設計文書（Blueprint）
         現場で使う記入式フォーマット／完成物の設計図
              ↑
階層4 ── 制作物
         記入済み文書・ケースブック本体・クライアント制作物
```

| 階層 | 区分 | 性質 | 代表文書 |
|---|---|---|---|
| 0 | 唯一の基準 | 不変。すべての源 | PHOSARA_MASTER_CONTEXT_v1.0_JP.md |
| 1 | 基盤文書 | 準不変。基準を具体化 | PHOSARA_COMPANY_GUIDE・PHOSARA_Brand_Book・PHOSARA_Wordmark_Guidelines |
| 2 | 運用文書（Guide） | 可変。思想と工程を定義 | Sales_Playbook・Business_Audit_Guide・PHOSARA_DESIGN_CONSULTING_GUIDE |
| 3 | 実務文書（Template）・設計文書（Blueprint） | 可変。現場で使用 | Proposal_Template・Estimate_Template・Contract_Template・各監査 Template・PHOSARA_Casebook_Blueprint・PHOSARA_Construction_Grid |
| 4 | 制作物 | 案件固有 | 記入済み各文書・業界別ケースブック本体・クライアント成果物 |

階層0の唯一の基準は、何も参照せず、すべてに参照される。階層が下がるほど、上位文書への参照が増える。

# 05 フォルダ構成


### 保存ルール

- 新規作成した資料は、役割に応じたフォルダへ保存する。
- 保存先に迷う場合は、本書のドキュメント一覧を優先する。
- 同一内容の資料を複数フォルダへ保存しない。

PHOSARAのすべての文書は、次の公式フォルダ構成に従って保管する。フォルダは機能で分け、一つの文書は一つのフォルダにのみ置く。同じ文書を複数の場所に複製しない。

```
PHOSARA
├── 00_ブランド基盤
├── 01_営業
├── 02_コンサルティング
├── 03_業界別ソリューション
├── 04_ケースブック
├── 05_デザインシステム
├── 06_テンプレート
├── 07_クライアント制作物
├── 90_アーカイブ
└── 99_旧バージョン
```

**各フォルダの役割**

| フォルダ | 役割 | 主な内容 |
|---|---|---|
| 00_ブランド基盤 | ブランドの源と基盤を保管 | 唯一の基準・会社の全体像・ブランド規定・ワードマーク規定 |
| 01_営業 | 営業システムの運用文書を保管 | セールス・プレイブック（営業工程の運用マニュアル） |
| 02_コンサルティング | 診断・設計の運用文書を保管 | 事業監査ガイド・デザインコンサルティングガイド |
| 03_業界別ソリューション | 業界別の解決の型と設計仕様を保管 | 建設・リフォーム・クリニック・パチンコの各ソリューション設計 |
| 04_ケースブック | ケースブックの設計図と本体を保管 | ケースブックの Blueprint・業界別ケースブック本体 |
| 05_デザインシステム | 視覚体系の規定を保管 | デザイントークン・グリッド・タイポグラフィ・コンポーネント規定 |
| 06_テンプレート | 記入式テンプレートのマスターを保管 | ヒアリングシート・各監査・提案・見積・契約の各 Template |
| 07_クライアント制作物 | 案件ごとの記入済み文書・成果物を保管 | クライアントデータを含む文書（社外区分） |
| 90_アーカイブ | 運用を終えた完成文書を保管 | 完了案件・廃止文書の長期保管 |
| 99_旧バージョン | 改訂で置き換えられた旧版を保管 | 版が上がり、運用を退いた旧ファイル |

**90 と 99 の区別**

- **99_旧バージョン** ── 現に生きている文書の、過去の版を保管する。最新版は機能フォルダに、旧版は 99 に置く。
- **90_アーカイブ** ── 役目を終えた文書（完了案件・廃止された文書）を保管する。もはや運用しないが、記録として残す。

# 07 ドキュメントの役割

PHOSARAの文書は、その役割に応じて三つの種別に分かれる。**Guide・Template・Blueprint** である。三つは、同じ唯一の基準から派生し、いずれも基準を再定義しない。役割が異なるだけである。

| 種別 | 役割 | 答える問い | 代表文書 |
|---|---|---|---|
| **Guide** | 考え方・原則・構造・工程を定義する | なぜ・何を・どの順で | Sales_Playbook・Business_Audit_Guide・PHOSARA_DESIGN_CONSULTING_GUIDE・PHOSARA_COMPANY_GUIDE |
| **Template** | 実務でそのまま記入・使用する記入式フォーマットを定義する | 現場でどう使うか | Proposal_Template・Estimate_Template・Contract_Template・各監査 Template・Client_Hearing_Sheet |
| **Blueprint** | 完成成果物を、寸法・グリッド・構成・体裁まで規定する設計図を定義する | どう正確に組むか | PHOSARA_Casebook_Blueprint・PHOSARA_Construction_Grid |

**三者の関係**

- **Guide が思想を定める。** 何を・なぜ・どの工程で行うかを示す。Guide は、Template と Blueprint の前提となる。
- **Template が運用へ移す。** Guide の思想を、現場でそのまま記入できる形に落とす。診断・提案・見積・契約は、この Template によって再現される。
- **Blueprint が完成形を確定する。** プレゼン品質の成果物を、誰が組んでも同じ体裁で再現できるよう、数値で固定する。

三者は上下ではなく分業の関係にある。Guide は「思想」、Template は「運用」、Blueprint は「設計」を担う。いずれも唯一の基準を参照し、その定義を変更しない。

*参照：PHOSARA_MASTER_CONTEXT（ビジネス・メソドロジー／提供構造）。*

# 08 ドキュメント間の参照ルール

文書間の参照は、一方向に保つ。参照の規律が、矛盾と循環を防ぐ。

**唯一の基準（Single Source of Truth）**

- **PHOSARA_MASTER_CONTEXT_v1.0_JP.md** が唯一の基準である。理念・ミッション・ビジョン・ポジショニング・コアバリュー・ブランドボイス・サービスアーキテクチャ・役務範囲の規律は、ここにのみ定義する。
- すべての文書は、これらをこの基準から参照する。他の文書で再定義しない。

**参照の方向**

- 参照は、下位の階層から上位の階層へ向かう。上位は下位を参照しない。
- 同位の文書間では、定義の重複を避け、役割の接続のみを参照する。
- 循環参照を禁じる。AがBを、BがAを「定義の源」として参照する状態をつくらない。

**参照の規律**

| 規律 | 内容 |
|---|---|
| 再定義しない | 上位文書の定義を、下位文書で書き換えない。参照する。 |
| 一元管理 | 一つの情報は、一つの文書だけが管理する。重複して持たない。 |
| 出典を明記する | 各文書の末尾に、参照した文書と版を記す。 |
| 整合を保つ | 提案・見積・契約のように連続する文書は、内容を相互に矛盾させない。 |

**営業フローにおける参照の連鎖（例）**

```
PHOSARA_MASTER_CONTEXT（唯一の基準）
   ↑ 参照
Sales_Playbook（運用の全体像）
   ↑ 参照
各監査 Template → Proposal_Template → Estimate_Template → Contract_Template
（前工程の結論を、後工程が転記・参照して接続する）
```

提案は監査の結論を、見積は提案を、契約は見積を参照して引き継ぐ。後工程は前工程の範囲を増やさず、矛盾させない。

# 09 命名規則

文書名は、公式の命名規則に従う。命名の統一が、検索性と版の取り違え防止を支える。

**基本構造**

```
［接頭辞_］名称_v［メジャー］.［マイナー］［_言語・版］.拡張子
```

| 要素 | 規則 | 例 |
|---|---|---|
| 接頭辞 | 全社共通の基盤・規定には `PHOSARA_` を付す。工程文書は付さないことができる。 | PHOSARA_MASTER_CONTEXT／Proposal |
| 名称 | 役割が分かる名称とし、末尾に種別語（Guide／Template／Blueprint 等）を付す。 | Estimate_Template／Business_Audit_Guide |
| 版 | `v［メジャー］.［マイナー］` 形式で記す。 | v1.0／v1.2／v3.0 |
| 言語・版 | 言語版・地域版は末尾に付す。 | _JP |
| 拡張子 | 形式に応じる。 | .md／.html／.docx／.pdf |

**版表記の補足**

- 公式の版表記は `v1.0` 形式（ドット区切り）とする。
- ファイルシステムの制約でドットを用いられない場合は、`v1_0` 形式（アンダースコア区切り）を等価として用いてよい。両者は同一の版を指す。

**命名の規律**

- 公式文書名は改変しない。版を上げる以外の理由で名称を変えない。
- 日付・担当者名・「最新」「最終」等の語をファイル名に含めない。版で管理する。
- クライアント制作物は、案件を識別できる接頭辞を付し、社外区分であることを明確にする。

# 10 バージョン管理

版は、文書の同一性を保ちながら、変更を追跡するために用いる。版の規律は、Sales_Playbook の版管理方針を継承し、全文書へ拡張する。

**版番号の意味**

| 版 | 意味 | 例 |
|---|---|---|
| v1.0 | 正式版。承認・公開された最初の確定版。 | 新規文書の公開時 |
| v1.1（マイナー） | 軽微修正。表記・誤記・補足の修正。構造・定義は変えない。 | 文言の修正 |
| v2.0（メジャー） | 構造変更。章構成・定義・運用の本質的な改訂。 | 工程やテンプレート構造の変更 |

**版運用の規律**

- 改訂は必ず版番号で管理し、旧版と取り違えない。
- 最新版を機能フォルダに置き、旧版は 99_旧バージョン へ移す。最新版は常に一つに保つ。
- 各文書の末尾に、版と出典を記す。
- 唯一の基準（PHOSARA_MASTER_CONTEXT）が更新された場合は、すべての関連文書の整合性を確認する（11 更新ルール）。

# 11 更新ルール

文書の更新は、影響範囲に応じて優先順位を定めて行う。優先順位は、印象ではなく、唯一の基準への近さで決まる。

**更新の優先順位**

| 優先度 | 対象 | 対応 |
|---|---|---|
| 最優先 | 唯一の基準（PHOSARA_MASTER_CONTEXT）の変更 | 変更を反映し、全関連文書の整合性を確認する。波及を放置しない。 |
| 高 | 役務範囲・ポジショニング・ブランドボイスに関わる変更 | 該当を参照するすべての文書を点検し、矛盾を解消する。 |
| 中 | 工程・テンプレート構造の実務変更 | 該当工程の Guide・Template を改訂し、前後工程との整合を確認する（メジャー版）。 |
| 低 | 表記・誤記・補足の修正 | 該当文書のみを修正する（マイナー版）。 |

**更新の手順**

1. 変更の影響範囲を特定する（どの文書が、この情報を参照しているか）。
2. 唯一の基準に変更がある場合は、まず基準を更新する。
3. 上位から下位へ、参照の連鎖に沿って整合を確認する。
4. 版を上げ、旧版を 99_旧バージョン へ移す。
5. ドキュメント一覧（06）と各文書末尾の出典を更新する。

**カスケードの原則**

唯一の基準の変更は、下流のすべてへ波及しうる。基準を更新したまま下流を放置しない。更新は、波及の確認を伴って初めて完了する。

# 12 新規ドキュメント追加ルール

新規文書は、体系に矛盾を持ち込まないことを条件に追加する。追加は、量を増やすことではなく、欠けている役割を埋めることである。

**追加の判断基準**

- その情報は、既存の文書で管理されていないか（重複を避ける）。
- どの階層・種別（Guide／Template／Blueprint）・フォルダに属するかが明確か。
- 唯一の基準を再定義していないか。参照のみで成立するか。
- 既存の命名規則・版管理に従えるか。

**追加の手順**

1. 役割・階層・種別・フォルダを確定する。
2. 命名規則（09）に従って名称を定め、初版を `v1.0` とする。
3. 唯一の基準および関連する上位文書への参照を、文書内に明記する。
4. 品質管理（14）のチェックを通過させる。
5. ドキュメント一覧（06）へ登録する。

**追加の規律**

- 新しい業界・エディションは、唯一のPHOSARAブランドの個別エディションとして扱う。理念を再定義せず、適応のみを行う。
- 一つの役割に一つの文書を対応させる。役割が曖昧な文書を増やさない。

# 13 廃止・アーカイブルール

文書の役目が終わったときは、削除ではなく、規律に従って退役させる。記録を残しつつ、運用を整理する。

**旧版の退役（99_旧バージョン）**

- 文書の版を上げたときは、旧版を 99_旧バージョン へ移す。
- 機能フォルダに残す最新版は、常に一つに保つ。

**文書の廃止（90_アーカイブ）**

- 役割を終えた文書（運用しなくなった Guide・Template・完了案件の制作物等）は、90_アーカイブ へ移す。
- 廃止する際は、その文書を参照していた他の文書を確認し、参照先を更新または除去する。参照の切れ目を放置しない。

**退役・廃止の規律**

| 規律 | 内容 |
|---|---|
| 削除しない | 文書は削除せず、99 または 90 へ移して記録を残す。 |
| 参照を清算する | 廃止前に、その文書への参照をすべて点検し、整合させる。 |
| 一覧を更新する | ドキュメント一覧（06）から運用中の記載を外し、所在を移す。 |
| 取り違えを防ぐ | 退役した文書を、運用中と誤認しない状態に保つ。 |

# 14 品質管理

すべての文書は、公開・改訂の前に品質の関門を通過する。品質は、感覚ではなく基準で確認する。

**三つの問い（唯一の基準より）**

文書もまた、PHOSARAの三つの柱に照らして点検する。

- **可視化** ── 必要な情報が、見える状態に整理されているか。
- **越境** ── 前版・前例の一歩先へ、明確さが進んでいるか。
- **本質** ── 不要な情報を削ぎ、核だけが残っているか。

**公開前チェックリスト**

| 確認項目 | 基準 |
|---|---|
| 唯一の基準への準拠 | PHOSARA_MASTER_CONTEXT に従っているか。 |
| 再定義の不在 | 上位の定義を再定義せず、参照のみで成立しているか。 |
| 役割の明確さ | 階層・種別・フォルダが明確か。 |
| 命名・版 | 命名規則・版表記に従っているか。 |
| 出典の明記 | 末尾に参照文書と版を記しているか。 |
| 整合性 | 関連文書（特に前後工程）と矛盾しないか。 |
| クライアントデータ | 創作したクライアントデータ・料金を含んでいないか。 |
| 記入記号の統一 | 記入式の場合、`［　］`・`〔A／B〕`・`□` を統一しているか。 |
| 社内・社外の区分 | 社内メモと社外文書を区別しているか。 |

**品質の規律**

- ブランドボイス（静か・明晰・知的・誠実・品位）を、文書の語り口にも適用する。
- 一画面一概念。情報を詰め込まず、余白で語らせる。書き出し前に最後の一割を削る。
- 品質を属人化させない。誰が確認しても、同じ基準で同じ結論に至る状態をつくる。

*参照：PHOSARA_MASTER_CONTEXT（ブランドエッセンス／コアバリュー／ブランドボイス）。*

# 15 運用ルール

文書管理システムは、日々の運用によって維持される。運用の規律と、文書の所有を定める。

**ドキュメント・ライフサイクル**

文書は、次の生涯をたどる。各段階で、定められた規律を満たす。

```
草案 → レビュー → 承認・公開（v1.0）→ 運用 → 改訂（v1.1／v2.0）→ 旧版を99へ → 廃止 → 90へアーカイブ
```

| 段階 | 内容 | 規律 |
|---|---|---|
| 草案 | 役割・階層・種別を定めて起草する | 12 新規追加ルールに従う |
| レビュー | 品質の関門を通す | 14 品質管理のチェックリスト |
| 承認・公開 | 正式版 v1.0 として公開する | 06 ドキュメント一覧へ登録 |
| 運用 | 機能フォルダで参照・使用する | 08 参照ルールに従う |
| 改訂 | 版を上げて更新する | 10・11 の版・更新ルール |
| 退役 | 旧版を 99 へ移す | 13 廃止・アーカイブルール |
| 廃止 | 役目を終えた文書を 90 へ移す | 参照を清算してから移す |

**ドキュメントの所有**

各フォルダ・文書には、内容に責任を持つオーナーを定める。オーナーは役割で定め、特定の個人名に依存させない。

| フォルダ | オーナー（役割） |
|---|---|
| 00_ブランド基盤 | ブランド責任者 |
| 01_営業 | 営業統括 |
| 02_コンサルティング | コンサルティング統括 |
| 03_業界別ソリューション | ソリューション統括 |
| 04_ケースブック | 制作統括 |
| 05_デザインシステム | デザイン統括 |
| 06_テンプレート | 各工程オーナー（ドキュメント管理責任者が一元管理） |
| 07_クライアント制作物 | 案件担当 |
| 90_アーカイブ／99_旧バージョン | ドキュメント管理責任者 |

**ドキュメント管理責任者の役割**

- 文書体系全体の整合・版・所在を統括する。
- 唯一の基準の更新時に、カスケードの確認を主導する。
- ドキュメント一覧（06）を最新に保つ。

**運用の規律**

- 各工程は、定められた成果物を文書として残す。記憶や口頭で接続しない。
- 社内メモ（担当所感・リスク・関係構築メモ）は、社外文書と区別し、社外に共有しない。
- 迷ったときは、三つの柱——可視化・越境・本質——に立ち返り、核まで削り戻す。

*参照：Sales_Playbook（Documentation Rules／PHOSARA Documentation Principle）。*

# 16 将来拡張方針

文書体系は、領域が広がるほど薄まりやすい。拡張は、中核を保ったまま、適応として行う。

- **中核の定義は不変とする。** 見えない価値を可視化するという定義は、いかなる拡張でも再定義しない。新たな業界・エディション・文書は、これを拡張するものであり、置き換えるものではない。
- **新市場は個別エディションとして扱う。** 業界別ソリューション・ケースブックは、唯一のPHOSARAブランドの個別エディションとして追加する。言語や事例は適応させ、本質は固定する。
- **フォルダ構成を保つ。** 拡張は、既存のフォルダの拡張枠（03 業界別ソリューション・04 ケースブック等）で受ける。むやみに新フォルダを増やさない。
- **一つの役割に一つの文書を保つ。** 拡張時も、重複を避け、役割と文書を一対一に保つ。
- **拡張ごとに整合を確認する。** 新規追加・改訂のたびに、唯一の基準との整合と、参照の連鎖を点検する。
- **量ではなく再現性で拡張する。** 文書を増やすことを目的とせず、再現可能な運用を広げることを目的とする。

迷ったときは、三つの柱——可視化・越境・本質——に立ち返り、核まで削り戻す。
